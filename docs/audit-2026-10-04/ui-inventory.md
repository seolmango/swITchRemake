# UI 독립 감사 — 최초 기능·성공 계약 목록

작성일: 2026-10-04. 최초 목록의 근거는 현재 `client/src/App.tsx`, 각 페이지/컴포넌트/스토어 소스다. 과거 대화·메모리·보고서·기존 테스트를 최초 근거로 사용하지 않았다. `D:\`, `D:\code`, 저장소 및 저장소 파일 검색에서 AGENTS.md가 발견되지 않았다.

이 문서는 조사 시점별 기록을 보존한다. 아래의 초기 `대기/미검증` 문구는 해당 단계의 상태이며, 이후 재실행 결과를 소급해 바꾸지 않았다. 현재 통합 판정은 [커버리지 표](README.md)와 [실행 결과](local-results.md)를 따른다. 10월 5일 최종 core9/9에는 실제 로그아웃 실패 복구와 리플레이 시간 진행·정지·탐색·손상 파일 복구도 포함된다.

## 역할과 공통 상태

- 익명/부트스트랩 중 → 게스트 또는 계정. 실패 시 복구 화면에서 재시도 가능해야 한다.
- 게스트: 공개 메뉴, 방·훈련·게임. 계정 전적/신고/MFA·기기 관리는 계정 안내로 대체되어야 한다.
- 계정: 로그인/MFA, 프로필·전적·세션·비밀번호·탈퇴, 경기 신고.
- 관리자: 서버 접근 판정과 개요/신고/검사 화면. 비관리자는 권한 거절 안내.
- 방 참가자: 호스트/플레이어/대기/관전자. 편집·시작·방장 위임·추방은 역할과 방 상태에 맞아야 한다.
- 모든 네트워크 화면: 로딩, 정상, 빈 결과, 실패, 재시도, 제한/만료, 연결 끊김·복구를 구분해야 한다. 늦은 응답이 새 화면/신원/선택의 성공 결과를 덮지 않아야 한다.
- 한국어/영어, 밝음/어두움, 고대비/색각/모션/키맵/터치 설정은 새 화면 및 새로고침 후 유지되어야 한다. 감사 중 모든 소리는 꺼 둔다.

## 우선 실제 사용자 여정

1. 게스트 진입 → 방 생성 → 다른 게스트 2명 입장 → 슬롯/스킬/맵 → 시작 → 이동·스킬 → 종료 → 결과 → 자동 로비 복귀 → 퇴장.
2. 가입(필수 동의·메일·사람 확인) → 로그인 → 프로필 → 비밀번호/MFA·신뢰기기 → 로그아웃 → 재로그인.
3. 도움말 → 훈련 → 설정 열기 → modifier 포함 이동키 설정 → 닫기 → 실제 이동 → 퇴장.
4. 모바일 세로 가입/설정 → 영어/어두움·저모션 → 탭/모달 키보드 이동 → 새로고침 후 설정 유지.
5. 결과에서 이미지 저장·신고 → 프로필 전적/리플레이 → 파일 재생/되감기.

## 다음 검증 방식

최초 목록 저장 이후 기존 테스트의 커버리지와 비교한다. 실제 UI/API/서버 성공 경로는 주 작업자의 조율 아래 격리된 로컬 테스트 데이터로 실행한다. Azure 요청 및 운영·비밀 데이터 접근은 수행하지 않는다. 소스만으로 의심되는 현상은 결함 확정과 구분한다.

## 의심 사항·설계 선택·미검증

- **의심, 미확정:** 로그인/가입/방 생성 등 여러 입력 화면이 HTML form 대신 div와 type=button을 사용한다. Enter 입력으로 제출되지 않는 예상은 있지만 버튼 키보드 접근 경로는 존재하므로 성공 차단 결함으로 확정하지 않았다.
- **의심, 미확정:** 회원가입 코드 발송 후 이메일과 재발송 버튼이 계속 disabled다. 코드 5분 만료/잘못 입력한 이메일의 복구 방법은 화면 새 진입뿐일 수 있다. 실제 시간 경과/SMTP 복구 시나리오는 아직 실행하지 않았다.
- **설계 선택:** 관리자 UI는 개요·신고·플레이어 조회·감사 로그를 제공하며 공지 변경 컨트롤은 없다. 홈의 읽기 공지 표시를 관리자 쓰기 기능의 성공으로 간주하지 않았다.
- **미검증:** 실제 MFA 이메일/TOTP·신뢰기기/백업코드, 외부 공유 선택기, 실제 브라우저 설치 흐름, 웹서비스워커 오프라인·다중탭, 리플레이 파일 변경/되감기, 모바일 터치 조합, 점검 중 활성 방 복구의 전체 사용자 여정은 담당 UI 신규 suite에 포함되지 않는다. 다른 감사 작업자의 완료 증거와 구분해야 한다.

신규 실행 파일: `e2e/audit/ui.spec.ts`. 격리 origin guard/무음 context, 비밀 로그·auth 스크린샷·trace/video 없이 총 4여정을 작성했다. 이 문서 작성 시점에는 독립 TypeScript 검증만 완료했고 실제 격리 스택 실행 결과는 주 작업자와 조율 중이다.

통합 후 추가 정상 인증 파일: `e2e/audit/account.spec.ts`. 합성 계정과 실제 두 브라우저로 비밀번호 변경·타 세션 무효·변경암호 재로그인, 이메일 MFA 등록·백업 저장 확인·실제 Mailpit MFA 로그인·신뢰기기 재로그인/해제·메일로 MFA 해제, 타기기 UI 재로그인/전체 폐기, 실제 Mailpit 탈퇴와 DB 익명화/세션 정리를 확인하도록 작성했다. 첫 실행 전과 여섯 번째 로그인 전에 각각 61초를 기다리며 기본 제한을 변경하지 않는다. 코드·백업코드는 메모리에만 보관하고 DB 조회는 synthetic 사용자 ID의 공개 상태/집계/익명화 boolean으로 제한한다. 독립 TypeScript 검증 완료, 실제 실행은 아직 미검증이다.

## 최초 격리 브라우저 실행에서 확인한 구분

CI 작업자가 공유한 첫 core 실행은 UI 4여정 중 가입·훈련·세로 설정 3개가 실패했다. 가입은 사람 확인 이후 코드 발송 완료 문구에 도달하지 못했고, 훈련은 HUD ready까지 도달하지 못했다. SMTP 설정 및 `http://web`의 Web Crypto secure context를 각각 통합 환경 담당자가 조사 중이다. 이것만으로 제품 결함을 확정하지 않는다. 다음 가입 실행은 `/api/auth/verify`의 HTTP status만 검사하여 서버 발송 실패와 DOM 기대 실패를 구분한다. 비밀 응답 본문·인증 화면 artifact는 남기지 않는다.

세로 설정 실패는 테스트 작성 오류로 확인했다. 실제 소스의 tab accessible name에는 시각적 번호 `<small>01</small>`도 포함되어 있으므로 정확한 이름은 `01 기본 설정`이다. UI의 키 맵핑, 확장 계정/MFA의 보안 탭에도 같은 오류가 잠복해 있었고 해당 선택자를 번호 포함 이름으로 수정했다. 제품 동작을 수정하거나 이 오류를 제품 결함 수에 더하지 않았다. 수정 후 실제 실행 결과는 아직 대기 중이며, 앞서 통과한 core TypeScript·lint·unit gate 증거는 유지한다.

설정 실제 suite는 desktop Chromium의 viewport를 390×844 → 844×390 → 1440×900으로 바꾸어 탭 접근·수평 overflow·언어/테마 유지를 확인하도록 확장했다. 이것은 viewport resize이며 실제 휴대전화, 터치 입력, 가상 키보드 또는 125% 브라우저 zoom 검증이 아니다. 이들 물리 기기/입력/zoom 시나리오는 미실행으로 남긴다.

CI의 backend/web/runner 재빌드 후 실제 UI 재실행은 **3 통과 / 1 실패**였다. 실제 SMTP 가입·필수 동의 영속화·로그인/프로필/로그아웃(6.6초), 390×844 설정의 키보드 탭·테마/언어 reload 유지(2.2초), synthetic 관리자 서버 개요·사용자 조회·감사 로그(2.7초)는 통과했다. 훈련은 secure context 허용 flag가 포함된 실행에서도 HUD ready가 60초 안에 나타나지 않아 미완료로 유지한다. 훈련 재실행에는 공개 loader 상태 boolean·Web Crypto 가용성·HTTP pathname/status·WebSocket event type/error enum만 저장하는 진단을 추가했다. viewport resize 확장은 첫 재빌드 이후 수정되어 위 3통과 증거에 포함하지 않는다. 계정/MFA/다중탭 확장 결과도 아직 이 통과 수에 포함하지 않는다.

CI의 실제 브라우저 probe로 동일 secure-origin flag에서 Chromium headless shell은 `isSecureContext=false, crypto.subtle=false`, 전체 Chromium channel은 두 값 모두 true임을 확인했다. 따라서 두 번째 훈련 실패를 제품의 맵 검증 결함으로 세지 않는다. 테스트 실행 브라우저를 전체 Chromium으로 바꿔 production HTTPS의 암호화 API 조건을 제공한 뒤 여정을 재실행해야 한다. 이 방식은 TLS/certificate 동작을 실제 검증했다는 뜻이 아니다.

## 실패한 로그아웃의 신원 보존

**UI-06(P1, HTTP/store 회귀로 확정):** 실제 서버 로그아웃 요청이 네트워크 오류/503으로 실패해도 `logoutAndCreateGuest`가 오류를 삼키고 새 guest를 발급해 계정 화면을 지웠다. 서버 세션과 refresh cookie의 폐기 확인은 없으므로 사용자가 로그아웃된 것으로 판단하는 화면과 서버의 로그인 상태가 달라질 수 있다. `useAuthStore.logout`도409 외 오류를 삼켜 정상 페이지 이동을 허용했다. 최초 최소 단위 6개가 모두 수정 전 실패했으며, 이는 실제 운영 세션에 접근한 증거가 아니라 mock HTTP에 대한 재현이다.

로그아웃은 기존 API의401 갱신 경로로 access token 만료와 서버 세션 폐기를 구분한 뒤 실제 acknowledgment를 받는다. 갱신 자체가401/403으로 거절되어 신원이 이미 anonymous로 바뀐 경우에만 이미 폐기된 경로로 새 guest를 발급한다. 네트워크/503/429/409 오류는 신원·refresh 상태를 보존하고 호출자에게 전달해 프로필에서 실패를 보여준다. 로그아웃 확인 후 guest 발급이 실패한 경우에는 anonymous/error를 유지하며 계정을 되살리지 않는다. store는 갱신으로 새로 받은 token도 보존한다.

수정 후 logout 단위 9개와 기존 auth9개 합계18개, client TypeScript·변경 파일 lint·audit TypeScript가 통과했다. account/guest 임시 실패 보존, access 만료의 정상 갱신/로그아웃, 이미 폐기된401, guest 발급 실패, 갱신 후409의 현재 신원 보존을 포함한다. `e2e/audit/userlogout.spec.ts`는 fresh synthetic account에서 오직 `/api/auth/logout` 전송만1회 abort하고 나머지 서버를 그대로 사용해 실패 표시/계정·DB 활성1·새 탭의 계정 유지 → 실제 재시도 acknowledgment/DB 활성0/새 탭 guest를 확인하도록 작성했다. 10월 5일 코드 `5c87efd`의 로컬 및 Actions 최종 core에서 실제 회귀도 통과했다. 전송 실패 때 회원 화면·DB 활성1·새 탭 회원을 유지하고, 정상 재시도201 후 DB 활성0·새 탭 guest를 확인했다. 최종 core는 총9/9이며 단위 결과와 별도로 기록한다.
