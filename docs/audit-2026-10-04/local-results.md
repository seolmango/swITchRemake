# 로컬 실행 증거와 한계

10월 4일 실행 결과와 10월 5일 후속 검증을 구분한 기록이다. `local-oct04`는 기존 개발 DB와 분리한 Docker Compose 프로젝트다. PostgreSQL/Redis/Mailpit/리플레이 저장소의 합성 데이터만 사용했다. 실행 중 애플리케이션 네트워크는 internal이며 브라우저 외부 요청도 탐지·차단한다. 실제 외부 메일 전달은 이 환경의 검증 대상이 아니다.

## 10월 5일 최종 코드 재검증

코드 `5c87efd88ecf664581b36e8422538cde8048d7fd`의 로컬 core는 **10gate 및 실제 브라우저9/9 통과, 347.154초, skipped/unexpected/flaky 각0, exit0**이다. 로컬 증거는 `e2e/artifacts/audit/local-oct04/core-passed-5c87efd/{summary,checks}.json` 및 `results/`에 보존했다. 같은 SHA의 [GitHub Actions37246119331](https://github.com/seolmango/swITchRemake/actions/runs/37246119331)도 **10gate 및9/9 통과, 266.003초, skipped/unexpected/flaky 각0**이다.

UI-06은 로그아웃 전송만1회 차단한 뒤 실패 표시·회원 유지·DB 활성세션1·새 탭 회원을 확인하고, 실제 재시도201·DB 활성0·새 탭 guest까지 통과했다. 리플레이는 정상 파일의 `검증됨` 서명 판정, 실제 재생 프레임 전진, 일시정지 뒤 위치 유지, 끝/처음 탐색, 작은 비정상 파일 거부 뒤 같은 화면에서 정상 파일 다시 열기와 서명·타임라인 복구를 확인했다. 앞선8/8의 버튼 상태 검사보다 강화한 결과다.

Actions artifact11318903275는7JSON·3합성PNG이며, 제한된 자격 증명/운영 Azure 패턴 검사0건과 raw logs 없음이 확인됐다. `e2e/artifacts/audit/github-core-37246119331/verification.json`에 정확한 SHA·단계·검사 범위를 보존했다. 전체 비밀 검출이나 앱의 패킷별 외부 요청 수를 측정했다는 뜻은 아니다.

## 10월 4일 핵심 사용자 여정

보존한 `e2e/artifacts/audit/local-oct04/core-passed-90cf598/`의 `checks.json`은 배포 정책, egress, 타입 검사 두 종류, lint, workspace 단위, 실제 브라우저의 7단계 모두 통과를 기록한다. `summary.json`의 실제 브라우저 결과는 **8/8 통과, 219.2초, skip 0, retry 0**이다. 후속 변경의 GitHub 검사 SHA와는 구분한다.

- 세 개의 별도 Chromium 프로세스와 별도 회원 신원으로 두 경기를 끝까지 수행했다. 각 경기에서 클라이언트의 실제 이동 입력과 서버 snapshot 좌표 변화를 함께 검사했다.
- 경기 식별자 `ab48abcb-d047-4194-bec3-88ad9c51eaed`, `c1ea81f6-2c17-4d8c-a904-2c7b28cee325`로 3명 결과 화면, API, PostgreSQL 참가자/승패/XP를 연결했다. 보상 기대값은 저장된 최종 숫자를 복사하지 않고 경기 시간과 규칙에서 계산했다.
- 다음 경기, 방장 이전, 전원 퇴장과 방 목록 제거를 확인했다. 실제 리플레이 파일의 권한 있는 다운로드, 일회성 티켓, 열기·재생 상태 진입을 검증했다. 기존 검사는 재생 버튼 상태까지만 확인하여 시간 진행·일시정지·탐색의 증거로 충분하지 않았다. 후속 core에 실제 프레임 진행/정지/양방향 탐색 및 작은 잘못된 파일 이후 정상 파일 복구 검사를 추가했고 위 10월 5일 최종 실행에서 해당 상세 동작도 통과했다.
- 실제 경기의 플레이어 신고를 관리자 화면에서 분류·경고 처리하고 DB/감사 기록 및 중복 처리 거부를 비교했다.
- UI 회원가입은 실제 사람 확인 화면과 로컬 SMTP 수신, 동의 DB 기록, 로그인·프로필·로그아웃까지 연결했다. 훈련장의 사용자 지정 modifier 이동은 실제 서버 위치 변화를 확인했다.
- 동일 회원의 두 탭에서 동시 갱신한 뒤 두 화면의 로그인 상태와 서버 세션을 확인했다. 독립 플레이어 수에 이 탭들을 포함하지 않았다.

소프트웨어 렌더러, runner 2 CPU/3 GiB/pids 512에서 다인원 검사는 제품 UI의 30fps·낮은 화질·75% 렌더 해상도를 선택했다. 단일 훈련의 기본 그래픽 검사는 별도 통과했다. 이 결과로 고화질 다인원 성능이나 실제 휴대폰 성능을 보장하지 않는다.

## 오류·보안·장애

실제 HTTP/WSS와 PostgreSQL을 사용하는 핵심 보안 여정 2개가 통과했다. 정상 origin/ticket/인증 사용을 먼저 확인하고, 다른 회원 결과·리플레이 접근 거부, 관리자 역할 거부, 메시지 경계, 옛 세션 폐기·갱신 경쟁과 중복 결과 저장을 대조했다. 파서의 제한된 속성 검사는 별도 계층 증거이며 전체 브라우저 성공으로 세지 않는다.

별도 bounded fault 실행은 **11항목 통과**했다. PostgreSQL 중단/재개 때 readiness 503→200과 세션 저장을 확인했다. Redis 중단 6초 동안 같은 게임 OS PID 하나가 유지되고 복구 후 준비 상태가 돌아왔다. match 프로세스 재시작 후 DB/세션 보존, 리플레이 저장소 쓰기 권한 실패와 권한 복구 후 실제 쓰기도 확인했다. 컨테이너의 상한을 설정했지만 CPU·메모리·디스크를 실제 고갈시킨 시험은 아니다.

## 확장 실행의 실패와 재검증

첫 계정·복구·운영 확장 실행은 **1 통과·3 실패**였다. 암호 변경, 이메일 MFA·신뢰기기·다른 세션 폐기, TOTP 등록/로그인, SMTP 비밀번호 재설정은 각 선행 단계에서 성공했다. 계정 화면의 포커스 유실은 실제 제품 결함으로 분리하여 수정했다. 빈 방 목록을 가시 영역으로 요구한 오류는 테스트를 고치고 실제 방 생성·입장·퇴장으로 복구를 증명하도록 강화했다. 복구 후 마지막 재로그인의 실패 원인을 구분하려고 다음 실행에 안전한 HTTP 상태 증거를 추가했다. 새 웹 빌드 후 같은 확장4개를 다시 실행해 **4/4 통과, 321.36초, retry/skip/flaky 0**을 확인했다. 탈퇴의 실제 SMTP·DELETE200·DB 익명화/세션0, TOTP 재설정 후 새 암호와 두 번째 요소로 로그인·최종 MFA 해제까지 성공했다. 증거는 `browser-account-recovery-operations-1791120876703.json`이다. 성공 실행의 HTTP metadata에는429나 추가 CAPTCHA가 없었지만 첫 복구 실패 원인을 소급 확정할 수는 없다. 원인 미확정 기록을 보존한다.

동적 증설의 최초 실행은 실제 worker 1→2를 확인했으나, 새 worker 방의 WebSocket 연결 경계에서 실패했다. 이 실행으로 1→2→1이나 이관 후 경기 보존을 통과 처리하지 않는다. 봇 도구에서 발견한 시작 명령 과다 재시도는 별도 수정했으며, 정상 제한을 유지하는 회귀가 통과했다. 제품 증설 경계와 봇 도구 오류를 분리했다. S8 수정 후 재실행은 **3.4분에 통과**했다. 실제 OS PID72→72+1547→72, 독립 게스트6명, 새 worker 접속(봇 재시도 없음), 방 이관/재접속, 원래 경기와 이관한 방의 경기 각각 PostgreSQL 참가자3명 저장을 대조했다. 이관된 claim이 원래30초 TTL을 넘어 갱신되는 것과 최종 정리도 확인했다. `scaling-passed.json`과 `scaling-processes.json`을 보존했다. Redis heartbeat만으로 프로세스 증감을 판정하지 않았다.

## 재현

전체 명령과 상한은 [격리 실행](../../deploy/audit/README.md), [봇 도구](bots.md)를 따른다. `node scripts/audit-stack.cjs run core`가 push/PR과 같은 격리 실행이다. 운영 주소나 운영 자격 증명이 상속되면 Docker 호출 전에 실패해야 한다. 임시 프로젝트만 정리하며 기존 개발 자원은 삭제하지 않는다.

증거는 실행별 `e2e/artifacts/audit/<AUDIT_RUN_ID>/`에 수집한다. trace/영상/자동 오류 DOM 스냅샷은 끄고, 공개 가능한 결과·상태·합성 화면만 남긴다. 실패, 환경 준비 실패, 선행 실패로 인한 미실행, 명시적 확장 job skip은 서로 다르다.


실제 봇 CLI도 prepare3→reuse3/방1/정상 시작1/10Hz 입력→3명 snapshot·game.end 수신→logout3 정리를 통과했다. 별도 seed의 wait-only1명에 stop 명령을 보내 정상 종료·logout1을 확인했다. 두 실행 후 worker1/방0/연결0이었다.

S7 bounded fault는 **41,446ms에 통과**했다. 정확한 audit 게임 자식 두 개만 일시 정지하고, Redis는 정상인 채 두 heartbeat가 모두 오래된 상태에서 실제 OS child2/max2가12초 유지되며 세 번째가 생기지 않음을 확인했다. 독립 복구 watchdog을 먼저 준비했고, finally에서 두 프로세스를 재개한 뒤 idle worker1로 복귀했다. 호스트나 Azure 프로세스에는 신호를 보내지 않았다.
