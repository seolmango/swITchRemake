## 1. 목표와 원칙

추가하려는 기능은 크게 세 덩어리다.

1. 운영자가 플레이어, 경기, 신고, 안티치트 신호를 한곳에서 조사하고 제재할 수 있는 운영자 페이지
2. 전지적 관전과 각 플레이어 시점을 지원하는 서버 권위 리플레이
3. 리플레이 링크 공유, 파일 내보내기, 유료 장기 보관

공통 원칙:

- 게임 판정과 리플레이 원본의 권위자는 인게임 서버다.
- 일반 클라이언트가 경기 중 전지적 상태를 받는 경로는 만들지 않는다.
- 리플레이는 경기 종료 뒤에만 공개한다. 진행 중인 경기의 공유 링크가 실시간 맵핵이 되어서는 안 된다.
- 한 경기의 리플레이 파일은 하나만 저장하고 참가자들은 그 파일을 참조한다.
- 운영자도 데이터베이스를 직접 수정하지 않는다. 모든 제재와 해제는 서비스 API를 지나고 감사 로그를 남긴다.
- 자동 안티치트 신호와 IP 일치는 조사 단서이지, 영구 밴의 단독 근거가 아니다.
- 로컬에 내려받은 파일의 수정을 막을 수는 없다. 대신 서버가 만든 원본인지, 내려받은 뒤 변경됐는지를
  암호학적으로 검증한다.

## 2. 전체 흐름

```text
                         ┌─ 참가자별 검열 스냅샷 ──> 플레이 클라이언트
인게임 서버 시뮬레이션 ─┼─ 관전자 스냅샷 ────────> 관전 클라이언트
                         └─ 권위 상태 + 이벤트 ────> ReplayRecorder
                                                        │
                                             chunk 압축·해시·서명
                                                        │
                                  Object Storage <──────┘
                                        │
                    ┌───────────────────┼────────────────────┐
                    │                   │                    │
               리플레이 페이지       파일 다운로드       운영자 조사 화면
                    │                                        │
              전지적/개인 시점                         신고·안티치트 신호
```

리플레이 기록은 특정 WebSocket 연결에 실제로 보낸 패킷을 복사하지 않는다. 접속마다 시야 검열과 델타
기준, backpressure로 생략된 frame이 다르기 때문이다. `ReplayRecorder`는 시뮬레이션의 권위 상태에서
연결과 무관한 단일 기록을 만든다.

## 3. 운영자 페이지

### 3.1 접근 통제

운영자 페이지는 일반 사용자 페이지와 인증 영역을 분리한다. 가능하면 별도 origin을 사용한다.

- 역할은 최소한 `support`, `moderator`, `security`, `admin`으로 분리한다.
- 모든 운영자 계정은 MFA를 요구하고 세션 수명을 짧게 둔다.
- 플레이어 조회, 원본 IP 열람, 리플레이 열람, 밴, 밴 해제를 각각 권한으로 나눈다.
- 영구 밴과 대량 제재는 재확인 또는 2인 승인을 지원한다.
- 누가 언제 어떤 이유로 어떤 정보를 열람하고 제재했는지 append-only 감사 로그에 남긴다.
- 밴은 삭제·수정하지 않고 별도의 해제 레코드를 추가해 과거 이력을 보존한다.

### 3.2 주요 화면

초기 운영자 페이지에는 다음 화면이 있으면 된다.

#### 대시보드

- 현재 접속자, 활성 방, 인게임 서버 상태
- 최근 경기 수와 비정상 종료율
- 미처리 신고 수와 오래 대기 중인 신고
- 안티치트 신호 발생량과 심각도 분포
- 최근 제재와 해제

#### 플레이어 조회

- 계정 ID, 현재 닉네임, 가입 시각, 계정 상태
- 최근 경기와 승패·탈락·술래·스위치 통계
- 연결 끊김, 재접속, 비정상 종료 비율
- 받은 신고와 제출한 신고, 기존 제재와 이의 제기
- 최근 안티치트 신호와 관련 경기
- 현재 접속 방과 활성 세션. 강제 로그아웃 및 활성 경기 퇴장 기능
- 최근 IP/대역, ASN·국가, 동일 IP 상관관계

#### 경기 조사

- 경기 메타데이터, 참가자, 규칙·맵·서버 빌드 버전
- 전지적 리플레이와 참가자별 시점 전환
- 시간축 위의 술래 변경, 탈락, 스킬, 재접속, 신고 지점, 안티치트 신호
- 특정 tick 북마크와 내부 조사 메모
- 리플레이 무결성·서명 상태

#### 신고 큐

- 심각도, 신고 종류, 누적 신고자 수, 관련 안티치트 점수로 정렬
- `OPEN -> TRIAGED -> REVIEWING -> ACTIONED/DISMISSED -> APPEALED -> CLOSED` 상태
- 중복 신고를 경기·대상별 사건 하나로 묶기
- 담당자 배정, 내부 메모, 처리 사유 템플릿

#### 제재 관리

- 경고, 기간제 게임 이용 제한, 영구 계정 밴
- 세션 전체 무효화, 현재 게임에서 퇴장
- 제한적인 임시 IP/CIDR 차단
- 시작 시각, 만료 시각, 범위, 근거 경기, 내부 사유, 사용자에게 보여줄 사유
- 이의 제기와 해제 이력

### 3.3 IP 취급

IP는 개인정보이면서 오탐이 많은 신호다. PC방, 학교, 회사, CGNAT, VPN 때문에 같은 IP가 곧 같은
사람을 뜻하지 않는다.

- reverse proxy가 검증한 실제 client IP만 신뢰한다. 임의의 `X-Forwarded-For`를 저장하지 않는다.
- 원본 IP는 짧은 기간 암호화 보관하고, 일반 운영 화면에는 기본적으로 마스킹한다.
- 장기 상관관계가 필요하면 서버 비밀키로 만든 `HMAC(normalizedIp)`를 별도로 저장한다. 단순 SHA 해시는
  IPv4 공간을 전수 대입할 수 있어 익명화가 아니다.
- 원본 IP 열람은 `security` 권한과 열람 사유를 요구하고 감사 로그에 기록한다.
- IP 단독 영구 밴은 하지 않는다. 공격을 멈추기 위한 짧은 rate limit·임시 차단에 우선 사용한다.
- 원본 IP, 파생 위치 정보, 감사 로그의 보존 기간과 파기 정책을 운영 전 개인정보 처리방침에 반영한다.

## 4. 신고와 조사 보존

### 4.1 신고 생성

신고는 사용자가 임의의 파일을 첨부하는 방식이 아니라 서버가 알고 있는 `matchId`를 대상으로 생성한다.

- 해당 경기 참가자 또는 허용된 관전자만 신고할 수 있다.
- 대상 플레이어, 분류, 설명, 사용자가 가리킨 replay tick을 받는다.
- 동일 신고자의 반복 제출을 제한하고, 허위·보복 신고 패턴도 집계한다.
- 신고가 경기 도중 접수되면 경기 종료 시 리플레이를 즉시 보존 대상으로 전환한다.
- 이미 끝난 경기는 무료 리플레이 열람 기간 안에서 신고할 수 있게 한다.
- 신고 접수 자체는 자동 제재 사유가 아니다.

### 4.2 보존 hold

평소 리플레이는 retention 정책에 따라 삭제될 수 있지만 신고된 경기는 `moderation hold`를 건다.

- 사건이 종료되고 이의 제기 기간까지 끝날 때까지 파일을 삭제하지 않는다.
- 같은 경기의 여러 신고는 같은 원본 파일을 공유한다.
- 운영자가 사건을 닫더라도 법적·보안상 별도 hold가 있으면 삭제하지 않는다.
- hold 추가·해제도 감사 로그에 기록한다.
- 개인정보 삭제 요청과 조사 보존 의무가 충돌할 때 적용할 운영 정책을 출시 전에 정한다.

## 5. 서버 안티치트

현재 구조는 서버가 위치, 속도, 충돌, 시야, 쿨타임을 판정하고 클라이언트는 입력만 보내므로 전통적인
속도 핵·좌표 변조·쿨타임 조작은 구조적으로 제한된다. 안티치트는 이 권위 모델을 대신하지 않고 그
경계에서 발생하는 이상 징후를 모은다.

초기 신호 예시:

- 입력·JSON 명령 rate limit 지속 초과
- 잘못된 길이, protocol version, sequence 역전이 반복되는 패킷
- 관전자나 탈락자가 이동·스킬 요청을 반복하는 행위
- 서버가 허용하지 않은 상태에서 방장·관전·스킬 명령을 반복하는 행위
- 사람의 입력으로 보기 어려운 장기간의 완전 동일 주기 입력 또는 매크로 패턴
- 시야에 들어온 직후의 반응 시간, 스위치 성공 패턴 등 통계적 이상치
- 다수 계정이 같은 IP·세션·행동 패턴으로 제재를 회피하는 정황
- 변조된 클라이언트 build 또는 protocol attestation 실패. 이것만으로 클라이언트 신뢰를 가정하지 않는다.

신호는 `severity`, `confidence`, `ruleVersion`, 관련 tick 범위를 갖는다. 확정적인 protocol 위반은 연결
종료나 짧은 자동 제한을 할 수 있지만, 행동 통계와 IP 상관관계는 운영자 검토 큐에 넣는다. 탐지 규칙이
바뀌어도 과거 판단을 설명할 수 있도록 적용 당시 `ruleVersion`과 원시 집계값을 함께 보존한다.

## 6. 리플레이 원본

### 6.1 기록 내용

경기당 리플레이 하나에 다음을 기록한다.

- replay format version과 생성 서버의 build ID
- protocol version, `rulesVersion`, `mapBundleHash`, visibility core version
- `matchId`, 시작·종료 tick, snapshot rate, 맵 ID
- 경기 시작 명단의 방 범위 `playerId`, 당시 닉네임, 색상
- 최초 full world state
- 위치·방향·상태 효과·술래·생존 상태의 delta frame
- 맵 변화, 자기장, 연막·수풀 등 시야 계산에 필요한 모든 권위 상태
- 스킬 사용, 술래 변경, 탈락, 이모지, 접속 해제·재접속 이벤트
- HUD 재현에 필요한 쿨타임과 경기 결과
- 선택적으로 서버가 실제 처리한 입력 기록. 디버깅과 판정 검증용이며 기본 재생의 유일한 근거로 삼지 않는다.

리플레이는 1~2초 단위 chunk로 나누고 각 chunk 첫 frame을 독립적인 keyframe으로 둔다. 탐색할 때 가장
가까운 keyframe부터 delta를 적용하고, 전체 파일을 처음부터 재생하지 않는다.

### 6.2 전지적 관전

전지적 모드는 권위 상태의 모든 플레이어를 그린다. 게임 중 관전자 모드와 같은 렌더링 계약을 쓰되,
리플레이 카메라는 자유 이동, 플레이어 추적, 확대·축소를 지원한다.

- 경기 종료 전에는 참가자에게 원본이나 공유 URL을 발급하지 않는다.
- `SELF`는 없고 사용자가 카메라 대상을 자유롭게 고른다.
- 운영자 화면은 안티치트 신호 tick과 신고자가 지정한 tick으로 바로 이동할 수 있다.

### 6.3 각 플레이어 시점

원본에 모든 권위 상태가 있으므로 과거 플레이어를 `viewerId`로 삼아 시야를 다시 계산할 수 있다. 다만
서버 시야 코드를 클라이언트에 손으로 복사해서 두 벌로 관리하면 시간이 지나며 결과가 달라진다.

권장 구조는 서버와 리플레이 플레이어가 같은 순수 visibility core를 사용하는 것이다.

```text
authoritative world state + viewerId + rulesVersion
                         │
                 versioned visibility core
                         │
       visible player mask + tile alpha overrides
```

- visibility core는 소켓, Phaser, 서버 room 객체를 모르는 순수 함수로 만든다.
- TypeScript shared package, WASM 등 하나의 소스에서 서버와 리플레이용 빌드를 만든다.
- 리플레이는 생성 당시의 visibility core version을 기록한다.
- 오래된 리플레이를 계속 지원하려면 과거 core를 함께 배포하거나, 서버에서 호환 변환본을 생성한다.
- 운영 조사에서 "당시 실제 서버가 무엇을 보냈는가"가 중요하므로 snapshot tick별 visible-player bitmask처럼
  작은 권위 판정 결과도 원본에 기록한다. 재계산 결과와 비교해 버전 오류를 탐지할 수 있다.
- 수풀 alpha까지 과거 화면과 완전히 같아야 한다면 해당 결과도 기록하거나 생성 당시 core를 반드시
  보존한다.

이 로직은 경기 종료 후 받은 원본에만 적용한다. 살아 있는 플레이 클라이언트에는 여전히 검열된
스냅샷만 보내므로 리플레이 기능이 실시간 시야 보안을 약화시키지 않는다.

### 6.4 재생 시간

현재 엔진의 이모지, 점멸, 카메라 효과는 로컬 경과시간을 사용한다. 제대로 된 일시정지·배속·탐색을
위해서는 리플레이 플레이어가 별도의 `playbackClock`을 소유해야 한다.

- pause, 0.5x/1x/2x, frame step
- tick 또는 millisecond 단위 seek
- seek 시 임시 연출과 카메라 보간 상태 초기화
- 이모지와 점멸 수명을 wall clock이 아니라 replay tick에서 계산
- keyframe 적용 뒤 목표 tick까지 delta와 이벤트 재적용

## 7. 링크 공유

공유는 파일 URL을 직접 공개하지 않고 애플리케이션의 share resource를 거친다.

```text
/replay/s/{unguessableToken}
        -> 공유 권한·만료·취소 상태 확인
        -> 리플레이 웹 플레이어
        -> 짧게 만료되는 object storage signed URL
```

- token은 충분한 난수로 만들고 DB에는 token 원문 대신 해시를 저장한다.
- 공개, 링크를 아는 사람, 특정 사용자 전용 범위를 지원할 수 있다.
- 만료 시각, 다운로드 허용 여부, 비밀번호, 최대 열람 횟수는 선택 기능이다.
- 생성자가 언제든 공유를 취소할 수 있어야 한다.
- 링크 페이지에는 당시 닉네임이 공개될 수 있음을 생성자에게 알린다.
- 원본 object storage key나 장기 credential은 브라우저에 노출하지 않는다.
- 신고·밴 증거용 내부 링크와 일반 공개 링크는 권한 체계를 분리한다.
- 공유된 경기라도 참여하지 않은 사용자의 계정 ID, IP, 내부 안티치트 신호는 절대 포함하지 않는다.

## 8. 파일 내보내기와 변조 검출

내보내기 확장자는 임시로 `.switchreplay`라 부른다. 파일은 실행 가능한 코드나 HTML이 아니라 제한된
binary container다.

예시 구조:

```text
magic + containerVersion
manifest
chunk index
compressed chunks
signature block
```

무결성 절차:

1. 각 chunk를 SHA-256으로 해시한다.
2. manifest에 chunk 해시, `matchId`, 버전, 길이, 생성 시각을 넣는다.
3. 서버의 오프라인 서명 키로 manifest를 Ed25519 서명한다.
4. 클라이언트는 내장되거나 서버에서 신뢰해 받은 공개키와 `keyId`로 서명을 검증한다.

체크섬만 넣으면 공격자가 내용을 바꾸고 체크섬도 다시 만들 수 있으므로 공식 파일 판별에는 전자서명이
필요하다. 개인키는 인게임 서버 프로세스마다 직접 배포하기보다, 파일 완성 후 제한된 signer service나
KMS가 서명하는 구조가 좋다.

검증 결과는 다음처럼 명확히 구분한다.

- `Verified`: swITch 서버가 서명했고 내용이 변경되지 않음
- `Modified`: 알려진 서명이 있지만 chunk hash가 일치하지 않음
- `Unverified`: 서명이 없거나 모르는 키로 서명됨
- `Unsupported`: 안전하게 파싱할 수 없는 미래/과거 형식

서명은 "이 바이트가 서버에서 생성된 뒤 변하지 않았다"는 것만 증명한다. 해당 사용자가 치트를 전혀
쓰지 않았다는 의미는 아니며 그 판단은 서버 판정과 안티치트·운영 조사 영역이다.

파일 파서는 신뢰할 수 없는 입력을 받는다고 가정한다.

- 전체 크기, chunk 수, 압축 해제 후 크기, 문자열 길이에 상한을 둔다.
- offset과 section length를 매번 검증한다.
- 압축 폭탄과 정수 overflow를 막는다.
- 파일 안의 URL이나 스크립트를 실행하지 않는다.
- 지원하지 않는 codec과 version은 오류로 끝내고 부분적으로 억지 재생하지 않는다.

## 9. 저장과 retention

메타데이터는 PostgreSQL, 압축 리플레이 blob은 S3 호환 object storage에 둔다. Redis에는 원본을 저장하지
않는다.

초기 무료 정책을 "최근 5경기 또는 종료 후 1시간 이내"로 정의하면 실제 조건은 합집합이다.

```text
user can access replay = rankAmongUserMatches <= 5 OR endedAt >= now - 1 hour
```

따라서 한 시간에 10경기를 하면 잠시 10개가 보이고, 오래 접속하지 않아도 마지막 5개는 남는다. 만약
"최대 5개이며 한 시간 뒤 삭제"를 원한다면 조건은 `AND`이고 상품 의미가 완전히 다르므로 출시 전에
확정한다.

파일 삭제 조건:

```text
무료 보존 자격을 가진 참가자가 없음
AND 유료 보관 없음
AND 활성 공유 정책상 보관할 필요 없음
AND moderation/legal hold 없음
-> object 삭제
```

한 참가자가 보존 자격을 잃어도 다른 참가자나 신고 사건이 파일을 붙들 수 있다. 그래서 물리 파일의
존재와 사용자별 열람 권한은 분리해 계산한다.

향후 BM 후보:

- 특정 리플레이 영구 보관 또는 보관 슬롯 확장
- 더 긴 경기 기록 이력
- 원본 파일 다운로드와 장기 공유 링크
- 주요 장면 북마크·클립 생성
- 경기 통계와 이동 경로 분석

신고 증거 접근과 이의 제기에 필요한 열람은 유료 기능과 분리한다.

## 11. 장애와 복구

- 게임 중에는 로컬 chunk를 bounded spool에 기록하고, 경기 종료 뒤 object storage에 업로드한다.
- object storage 장애 중에도 게임 판정은 계속하되 spool 한도를 넘기면 신규 경기 시작을 막는다.
- 업로드 성공과 DB metadata commit 사이에는 outbox를 사용해 재시도와 멱등성을 보장한다.
- 파일은 `recording -> finalizing -> available -> deleting/deleted` 상태를 갖는다.
- 서명 전이나 일부 chunk만 올라간 리플레이는 사용자에게 노출하지 않는다.
- 신고가 들어온 경기의 업로드 실패는 일반 리플레이보다 높은 우선순위로 경보한다.

## 12. 구현 순서 제안

코어 서버가 완성된 뒤 다음 순서가 자연스럽다.

1. `ReplayRecorder` 경계와 versioned manifest만 게임 서버 설계에 포함
2. 전지적 스냅샷 기록, chunk/keyframe, 로컬 재생 도구
3. object storage 업로드, 경기 결과와 replay metadata 연결
4. 웹 리플레이 플레이어의 재생·일시정지·탐색·배속
5. shared visibility core와 플레이어별 시점
6. 최근 5경기/1시간 retention과 사용자 경기 기록 화면
7. 신고 접수와 moderation hold
8. 최소 운영자 페이지, 감사 로그, 제재 API
9. 안티치트 신호와 리플레이 timeline 연동
10. 링크 공유와 취소·만료
11. 서명된 `.switchreplay` 내보내기와 안전한 import
12. 유료 장기 보관·분석 기능

초기부터 전부 만들 필요는 없지만 1번의 version 정보와 recorder 경계를 늦게 추가하면 이미 구현된 게임
루프, 결과 저장, protocol을 다시 뜯게 된다. 실제 녹화 기능은 뒤로 미뤄도 이 두 항목은 인게임 서버를
만들 때 함께 결정하는 편이 낫다.

## 13. 출시 전 결정할 사항

- 무료 retention이 `OR`인지 `AND`인지
- 링크 기본값이 비공개인지 unlisted인지, 공개 검색을 허용할지
- 파일 다운로드를 무료로 줄지 보관 상품에 포함할지
- 과거 visibility core를 클라이언트에 얼마나 오래 포함할지
- 신고 가능 기간과 사건 종료 뒤 증거 보존 기간
- 원본 IP, HMAC IP, 리플레이, 운영 감사 로그 각각의 보존 기간
- 사용자가 공유한 리플레이에서 당시 닉네임을 숨길 수 있게 할지
- 공식 파일이 아닌 `Unverified` replay import를 허용할지
- 기간제·영구 밴의 승인 수준과 이의 제기 절차
