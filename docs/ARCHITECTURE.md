# swITch 아키텍처 문서

swITch의 레포 구조, 서버 역할 분리, 통신 방식, 그리고 인게임 네트코드 원칙을 정의한다. 게임 규칙은 `GAME_DESIGN.md`, REST 엔드포인트는 `API_SPEC.md`, WebSocket 규약은 `WS_PROTOCOL.md`를 참고.

이 프로젝트는 과거에 완성했다가 **확장성·트래픽 병목** 때문에 갈아엎은 이력이 있다(→ `../legacy/`). 이 문서의 설계 결정은 대부분 "레거시가 왜 안 됐는가"에 대한 답이다. §9에 그 병목과 대응을 정리했다.

> 운영 전제: 매치 서버는 **당장은 1대로 운영**하되, 상태를 프로세스 메모리가 아닌 **Redis/Postgres에 두어 무상태로 설계**한다. 그러면 나중에 인스턴스를 늘리는 것이 코드 수정 없는 배포 문제가 된다. 게임 서버는 **동적으로 생성/삭제**될 수 있다.

## 1. 전체 구조

```
                         ┌──────────────┐
                         │   client     │  React (메뉴/로비/HUD) + Phaser (인게임)
                         └──────┬───────┘
                    REST/인증    │    WebSocket(인게임)
                 ┌──────────────┼───────────────┐
                 ▼                              ▼
        ┌─────────────────┐            ┌─────────────────┐
        │  server-match   │            │   server-game   │  (N개 인스턴스)
        │  NestJS/Fastify │            │   WebSocket     │
        │  인증 · 매치메이킹 │            │   권위적 시뮬레이션 │
        └───┬─────────┬───┘            └────┬────────┬───┘
            │         │                     │        │
       ┌────▼───┐ ┌───▼─────────────────────▼──┐
       │Postgres│ │          Redis             │
       │계정·세션 │ │ 인증코드·매치티켓·방/게임서버   │
       │·전적    │ │ 레지스트리·결과스트림          │
       └────────┘ └────────────────────────────┘
```

- **client**: 브라우저. 로비까지는 REST로 매치 서버와, 인게임에서는 WebSocket으로 게임 서버와 통신.
- **server-match**: 계정 인증 + 매치메이킹. HTTP(REST). 상태를 거의 갖지 않아 수평 확장 가능.
- **server-game**: 실시간 인게임 서버. WebSocket. **권위적(authoritative)** 시뮬레이션. 여러 인스턴스로 확장하며, 각 인스턴스가 다수의 방을 호스팅.
- **Redis**: 두 서버군이 공유하는 조율 계층(휘발성 상태 + 레지스트리 + 결과 스트림). 매치↔게임 직접 RPC는 없다(§5).
- **Postgres**: 영구 데이터(계정·전적).

### `shared` 패키지 — 단일 진실 공급원(SSOT)

- **DTO/도메인 타입**: 유저·방·매치 티켓·스킬·역할 등 공용 타입.

> 현재 `shared`는 `package.json`만 있고 알맹이가 없다. `index.ts` + 빌드 설정을 갖춰 실제 export를 제공해야 한다.

## 3. 데이터 스토어 역할 분담

| 스토어 | 담는 것 | 성격 |
|---|---|---|
| **Postgres** | 계정(이메일·비번해시·닉네임·`account_status`), 영구 전적(`stats`), **세션(`sessions`)·로그인 이력(`login_history`)** | 내구성 필요, 영구 |
| **Redis** | 이메일 인증코드, 매치 티켓, 방 레지스트리, 게임서버 레지스트리, 매치 결과 스트림 | 휘발성, 빠름, TTL 활용 |

원칙:
- **게임 진행 중 실시간 상태(플레이어 좌표 등)는 어느 DB에도 매 틱 쓰지 않는다.** 그건 게임서버 프로세스 메모리(방 객체) 안에만 있고, 종료 시 결과만 영구화한다.
- **세션(=리프레시 토큰)은 Postgres에 둔다**(휘발성이 아니라 기기 관리·보안 이력이 필요하므로). Redis에는 인증코드·티켓처럼 진짜 휘발성만. DB 부하는 낮다 — 일반 요청은 DB를 안 타고(무상태 JWT 검증), refresh는 기기당 15분에 1회 O(1) 조회뿐. 상세 → §4.

## 4. 인증 · 세션 · 계정

엔드포인트 전체는 `API_SPEC.md`. 여기선 개념·모델을 정의한다.

### 토큰
- **Access 토큰**: JWT, 수명 **15분**, payload `{ sub: userId, sid: sessionId }`. 일반 요청은 이 서명만 검증(무상태, DB 미접근).
- **Refresh 토큰**: JWT, 장수명(예: 30일), httpOnly·signed 쿠키. payload에 `sid` 포함.
- 회원가입: 이메일 인증코드(Redis, TTL 5분) → bcrypt 해시 → 유저 생성. 중복은 `constraint_name`으로 판별해 409.

### 세션 = 기기당 refresh 레코드 (멀티 기기 지원)
로그인 = **세션 1개 생성**(기기당 1개). Postgres에 저장.

| 테이블 | 용도 |
|---|---|
| `sessions` | 활성 세션. `(sid, user_id, refresh_token_hash, ua, ip, label, created_at, last_used_at, expires_at, revoked_at)`. 기기 관리 UI·원격 로그아웃용 |
| `login_history` | append-only 보안 감사. `(user_id, event_type, ip, ua, created_at)`. **인증 이벤트 때만** 기록(refresh·플레이 때 안 씀) |

- **refresh**: 세션 조회 → 저장 토큰과 대조 → **회전**(같은 sid, 새 토큰) → `last_used_at` 갱신. 기기당 15분에 1회라 부하 미미.
- **재사용 감지**: 이미 회전되어 폐기된 refresh 토큰이 제시되면 **도난 신호로 간주** — 해당 세션 즉시 폐기 + `login_history`에 보안 이벤트 기록. (회전만 하고 재사용 감지를 안 하면 도난 탐지 기회를 버리는 것.)
- **원격 로그아웃**: 해당 세션 삭제 → 그 기기는 refresh 불가. 단 이미 발급된 access는 **만료(≤15분)까지 유효**(무상태의 한계, 허용된 트레이드오프).
- **멀티 로그인 허용, 단 동시 게임은 계정당 1개**: 매치메이킹이 `playing:{userId}` Redis 키를 검사(§5). 게스트 미적용.

### 계정 상태 (소프트 삭제 + 밴)
`users.account_status`: `ACTIVE` / `DELETED`(자가삭제) / `BANNED`(관리자 정지) + `status_changed_at`.
- **DELETED**: 로그인 차단 + 전체 세션 종료. **N일 유예**(복구 가능·재가입 불가) 후 퍼지 잡이 **익명화**(email/nickname 치환) → unique 해제 → 같은 이메일 재가입 허용.
- **BANNED**: 익명화 안 함·영구 유지 → **재가입 영구 불가**. 퍼지 잡은 DELETED만 건드림.
- 로그인·조회는 `account_status = ACTIVE`만 통과.

### 게스트
비로그인도 플레이 가능(가벼운 웹게임 목표). 게스트는 닉네임 자유 입력(형식 검증, 유일성 없음), 스탯 미저장, 티켓에 `userId` 대신 임시 `guestId`. 서버가 플레이어마다 `isGuest`를 제공해 클라가 게스트 닉네임을 다른 색으로 렌더.

### 게임서버 WebSocket 인증
게임서버는 **상태 없는 JWT 검증 + 티켓**으로 접속을 인증한다(인증 DB 미의존).
- **최초 입장**: 매치 티켓(§5) + Access 토큰(또는 게스트 닉네임). 티켓 1회 소비(Redis), 로그인이면 `JWT_ACCESS_SECRET`으로 서명 검증 후 **JWT `sub` == 티켓 `userId` 대조**(불일치 = 거절 — 티켓 유출 시 다른 계정이 자리를 차지하는 것 방지).
- **재접속**(로그인 한정): Access 토큰 + roomId. userId로 `RECONNECTING` 슬롯 복귀(티켓 불필요). **슬롯이 `RECONNECTING` 상태일 때만 수락** — 원 연결이 살아있으면 거절(토큰 탈취로 진행 중 게임 세션을 가로채는 것 방지). 상세 → §5 방 생명주기, `WS_PROTOCOL.md`.

### 전송 보안 · 개인정보
- 프로덕션은 **HTTPS/WSS 필수** — 티켓·토큰이 평문으로 노출되면 인증 모델 전체가 무너진다.
- refresh 쿠키는 httpOnly·signed·`sameSite`. **클라와 API의 도메인 구성이 정해지면 strict/lax를 확정할 것** — 서로 다른 도메인이면 strict는 쿠키가 전송되지 않아 refresh가 통째로 깨진다. CORS 허용 오리진은 클라 도메인만.
- `login_history`의 IP/UA는 개인정보 — **보존 기간(예: 90일) 경과분 삭제 잡**을 두고, 계정 익명화(퍼지) 시 **해당 유저의 login_history IP/UA도 함께 익명화**한다(users 테이블만 익명화하면 불충분).
- 닉네임(특히 게스트 자유입력)은 타인에게 노출되는 유저 콘텐츠 — 필터링은 MVP 이후 과제로 인지해 둔다.

## 5. 매치메이킹 & 게임서버 핸드오프

매치 서버는 **직접 게임을 진행하지 않는다.** 매칭시켜 게임서버로 넘기는 역할만 한다. 핵심 설계: **로비(대기실)도 게임서버가 담당**하고(클라는 로비~인게임을 WS 연결 하나로 사용), **방은 첫 입장 시 지연 생성**한다. 그래서 매치서버↔게임서버 간 **직접 RPC가 없고**(Redis 레지스트리만으로 조율) 별도 매치 큐도 없다.

### 핸드오프 흐름 (지연 방 생성, RPC 없음)
```
① 게임서버 기동 → Redis: gameserver:{id}={url,load,heartbeat} + gameservers(set). 몇 초마다 heartbeat 갱신(TTL, 죽으면 자동 제거).

② 클라 "방 만들기"/"빠른매칭"/"코드참가" → 매치서버(REST)
   - gameservers에서 최소부하 서버 선택(빠른매칭은 rooms:public:waiting에서 빈 공개방 먼저 검색)
   - roomId(+roomCode) 생성, Redis에 room:{roomId}·roomcode:{code} 기록
   - ticket:{ticket}={userId 또는 guestId, roomId, gameServerId, nickname} (짧은 TTL, 1회용)
   - 클라에 반환: { gameServerUrl, roomId, ticket }

③ 클라 → 해당 게임서버(WS) 접속, { ticket, accessToken? / guestNickname? }

④ 게임서버: ticket 1회 소비·검증 → (로그인)JWT 검증 → 방 없으면 지연 생성, 있으면 합류
   → 플레이어 추가 후 room:{roomId}의 playerCount/state 등을 Redis에 갱신(매치서버가 볼 진실)

⑤ 방이 비면 게임서버가 room:{roomId}·roomcode:{code} 삭제 + 메모리 방 파괴.
```

### Redis 구조
| 키 | 내용 | 쓰는 주체 |
|---|---|---|
| `gameserver:{id}` / `gameservers`(set) | `{url, load, heartbeat}` / 살아있는 서버 id | 게임서버(heartbeat) |
| `room:{roomId}` | `{gameServerId, state, isPublic, hasPassword, playerCount, maxPlayers, ownerSlot, mapId, name}` | 게임서버(상태 변화 시) |
| `roomcode:{code}` | `roomId` | 게임서버(방 생성 시) |
| `rooms:public:waiting`(set) | 참가 가능한 공개·대기 방 id | 게임서버(공개/상태 변화 시) |
| `ticket:{ticket}` | 1회용 배정 토큰 | 매치서버 |

- **왜 RPC가 없나**: 매치서버는 게임서버 응답이 필요 없다. Redis에 슬롯을 예약하고 티켓만 주면, 게임서버는 티켓 든 클라가 올 때 자기 할당을 "발견"한다.
- **유령 방 방지**: 매치서버가 만든 `room:{roomId}`·`roomcode:{code}`는 **활성화(첫 입장) 전까지 짧은 TTL**을 가진다. 게임서버가 첫 입장을 처리할 때 TTL 해제(PERSIST). 아무도 접속하지 않으면 자동 소멸 — 비인증(게스트) 방 생성 스팸으로 Redis 키가 무한히 쌓이는 것을 막는다(방 생성 레이트리밋과 이중 방어).
- **동시 게임 1개(로그인)**: `playing:{userId} = roomId` **Redis 키(TTL)** 로 관리 — 게임서버가 입장 시 설정·주기 갱신, 퇴장/방 파괴 시 삭제. 매치 요청 시 이 키가 있으면 거부. **TTL 덕분에 게임서버가 크래시해도 자동 해제**되어 유저가 매치메이킹에서 영구히 잠기지 않는다. 게스트 미적용.
- **방 비밀번호**: `room:{roomId}` 레코드에 저장하고 매치서버가 join 시 검증(1~8자 방 비번 수준이라 평문 허용 — 계정 비밀번호와는 무관한 값).
- **엣지**: 티켓 발급 후 게임서버 사망 → 클라 접속 실패 → 재매칭(heartbeat TTL로 죽은 서버는 후보에서 빠짐). 정원 최종 권위는 게임서버(Redis playerCount는 힌트, 초과분 접속 거절).

### 방 생명주기 (게임서버 내부)
```
WAITING ──startGame(방장,최소3명)──▶ STARTING(카운트다운) ──▶ IN_GAME ──종료──▶ 결과(오버레이)
   ▲                                                                              │
   └───────────────────────── 같은 방으로 복귀(카트라이더식) ◀───────────────────────┘
방은 "비었을 때"만 파괴. 한 판 끝나도 방 유지, WAITING 복귀(재매칭 아님).
```
- **시작 = 방장 수동**(퀵매칭 포함, 자동 시작 없음). 최소 3명, 최대 8명. **준비(ready) 개념 없음** — 카운트다운(STARTING)이 오시작을 방지.
- **STARTING(카운트다운) 규칙**: 카운트다운 시작 = "게임이 시작된 판정". 이후 입장자는 다음 판 대기(관전 가능). 카운트다운 중 이탈로 3명 미만이 되면 취소 → WAITING 복귀.
- **게임 중 입장**: `IN_GAME`(또는 STARTING) 방에 들어오면 "다음 판 대기" + **관전 버튼**으로 진행 게임 관전(정원 8 내 슬롯 보유). 순수 관전 전용 슬롯은 MVP 제외.
- **아웃 → 자동 관전**(그 판 한정). 관전은 **플레이어 시점 / 자유 카메라** 두 모드 자유 전환(→ `WS_PROTOCOL.md`). **채팅 없음**(트래픽·필터링 부담, 나중에).
- **방장 이탈 시 자동 위임**: 방장이 나가거나 끊기면 남은 인원 중 가장 낮은 슬롯에게 자동 위임 + 브로드캐스트(수동 `passOwner`와 별개).
- **재접속(로그인 한정)**: 끊기면 즉시 아웃 아님 — 10초 제자리 정지(여전히 충돌·아웃 대상), 다른 이에겐 "접속끊김" 표시. 10초 내 재접속 시 재개, 초과 시 아웃. 끊긴 유저가 술래면 즉시 강제 술래 교체(게임 정지 방지). 게스트는 재접속 불가. 상세 → `WS_PROTOCOL.md`.

## 6. 인게임 네트코드 원칙 (server-game)

레거시 병목의 핵심이 여기였으므로, 다음을 **설계 불변식**으로 삼는다.

1. **권위적 서버 · 입력만 전송**: 클라이언트는 **좌표가 아니라 입력(이동 방향·스킬 발동)**만 보낸다. 서버가 시뮬레이션의 유일한 진실이다(일관성 + 안티치트). 레거시는 클라가 이동량(Δ)을 보내는 반권위적 방식이었다 — 이를 입력 기반으로 전환.
2. **시뮬레이션 틱과 전송률 분리**: 시뮬레이션은 60Hz로 돌리되, 스냅샷 브로드캐스트는 **20~30Hz**로 낮춘다. 클라이언트는 스냅샷 사이를 **보간(interpolation)**한다. **MVP는 보간만**(클라 예측 없음 → 입력 시퀀스 번호 불필요); 반응성이 부족하면 나중에 예측+보정을 얹는다. → 레거시는 이벤트루프가 도는 대로 무제한 브로드캐스트했다(`setTimeout(fn)` 무지연 재귀). 이것부터 없앤다.
3. **입력도 변화가 있을 때/제한된 레이트로만 전송**: 클라가 매 프레임 무조건 전송하지 않는다.
4. **관심 영역(AoI) & 시야 컬링**: 각 클라이언트에게 **그가 볼 수 있는 것만** 보낸다. 수풀/연막 뒤의 플레이어 좌표는 애초에 전송하지 않는다 — 대역폭 절감이자 안티치트(숨은 적 위치 노출 방지). 8인 방이라 이득이 작아 보여도 원칙으로 유지.
5. **맵은 스트리밍하지 않는다**: 자기장/타일 변화는 맵 빌드 시 **결정론적 타임라인**으로 사전 계산되어 클라가 이미 갖고 있다. 서버는 게임 시작 시각만 합의하면 되고, 맵 격자를 전송할 필요가 없다. → 레거시는 매 틱 맵 전체(2D 배열)를 전송했다. 이 병목은 맵 도구 단계에서 이미 구조적으로 제거됨(→ `GAME_DESIGN.md` §7, `MapBuilder`).
6. **핫패스는 바이트 정렬 바이너리**: 입력·스냅샷은 **바이트 정렬 바이너리**로 보낸다(서브바이트 비트패킹은 복잡도 대비 이득이 작아 하지 않음, 필요 시 나중에 조각). 로비·이벤트 등 저빈도 메시지는 JSON으로 시작해도 무방. 모든 메시지 타입·레이아웃은 `shared`에 정의. 상세 → `WS_PROTOCOL.md`.
7. **방 단위 캡슐화**: 각 방은 자기 상태(플레이어·타이머·자기장 진행)를 담은 **독립 객체/클래스**다. 레거시처럼 프로세스 전역 고정배열(`PlayerMaxNum=100`, `RoomMaxNum=16`)에 흩어 놓지 않는다. 이래야 한 프로세스가 다수 방을 깔끔히 다루고, 방 생성/소멸 라이프사이클이 명확해진다.

### 결정론적 이벤트 vs 전송 이벤트

- **전송 불필요(양쪽이 스스로 계산)**: 자기장 진행, 타일 변화, 쿨타임 진행.
- **전송 필요(비결정론적)**: 플레이어 위치/속도 스냅샷, 아웃, 술래 변경, 스킬 발동 효과, 접속/이탈, 게임 종료.

## 7. 클라이언트 구조 (React + Phaser)

| 계층 | 담당 | 도구 |
|---|---|---|
| **React** | 라우팅, 타이틀·로비·매칭·결과 화면, 설정, HUD 오버레이(스킬 쿨타임·알림·플레이어 목록) | react-router, Zustand, i18next |
| **Phaser** | 인게임 월드 렌더링(맵 타일·플레이어·스킬 이펙트·카메라·시야/포그) | Phaser (예정) |
| **네트워크 계층** | WS 연결 관리, 스냅샷 디코드/보간, 입력 송신 | `shared` 프로토콜 사용 |

- React는 UI/화면 전환을, Phaser는 실시간 캔버스를 담당하는 **명확한 경계**를 둔다. Phaser 씬은 네트워크 계층이 노출하는 상태를 구독해 렌더만 하고, 게임 판정은 하지 않는다(서버 권위).
- 현재 `GameContainer`는 1920×1080 고정 DOM 스케일링 방식이다. 메뉴에는 유지 가능하나, 인게임은 Phaser 캔버스로 대체/내장하는 방향을 검토(TBD).

## 8. 매치 결과 처리

게임 종료 시 통계(킬·switch 성공률·생존 순위 등)를 영구 전적에 반영한다. 게임서버는 실시간에 집중하고 **계정 DB를 직접 만지지 않는다.**

```
게임 종료 → 게임서버: XADD matchresults * <결과 JSON>   (Redis 스트림, fire-and-forget, AOF로 영속)
매치서버 워커: 스트림 소비 → Postgres 반영, 실패 시 재시도 → ACK
```

- **왜 스트림인가**: 게임서버가 **동적 생성/삭제**되어도 Redis 연결만 있으면 됨(Postgres 미접근) → 커넥션·보안 경계 깔끔. 게임서버가 결과 push 직후 죽어도 결과는 Redis에 남아 **유실 없음**, 재시도는 매치서버가 중앙 처리. 계정 DB 소유는 매치서버 단독.
- 게임 중 스탯은 게임서버 메모리에 두고, 종료 시점에만 스트림으로 flush. **게스트는 스탯 미반영**.
- **멱등성(중복 반영 방지)**: 결과에 게임서버가 생성한 고유 `matchId`를 포함하고, 워커는 `matchId`로 중복을 차단한다(처리 이력 테이블 unique 제약). 워커가 "Postgres 반영 → ACK" 사이에 죽고 재시도하면, 이게 없을 경우 wins/kill이 이중 집계된다.

> **미정(TBD)**: 경험치/레벨 공식(→ `GAME_DESIGN.md` §10). 매치당 갱신 항목(games+1, 생존 시 wins+1, kill·sw_su/sw_try·death_order)은 확정, level/xp 산식만 추후.

## 10. DB 스키마 변경 (계획)

현재 `server-match/src/database/schema.ts`는 `users`(id·email·passwordHash·nickname·stats jsonb·createdAt·updatedAt)만 있다. 필요한 변경:

- `users`: **`account_status`**(ACTIVE/DELETED/BANNED) + **`status_changed_at`** 추가(소프트 삭제·밴, §4).
- 신규 **`sessions`**: `(sid, user_id, refresh_token_hash, ua, ip, label, created_at, last_used_at, expires_at, revoked_at)` — 멀티기기·원격 로그아웃.
- 신규 **`login_history`**: `(user_id, event_type, ip, ua, created_at)` — append-only 보안 감사. 보존 기간 정책(예: 90일 후 삭제 잡) + 계정 익명화 시 IP/UA 함께 익명화(§4 전송 보안·개인정보).
- 신규 **`processed_matches`**: `(match_id UNIQUE, processed_at)` — 결과 워커 멱등 처리(§8).
- `stats`는 jsonb 유지(리더보드가 필요해지면 별도 테이블 분리 검토).
- 스키마는 클라·서버가 공유해야 하므로 결과 워커/게임서버가 접근할 부분은 `shared` 또는 공용 위치로 이동 검토.

## 11. 현재 코드 상태 & 다듬을 지점

- `shared`: 알맹이 없음 → 프로토콜·상수·타입을 채우는 것이 **다음 우선 작업 후보**.
- `server-game`: 빈 스텁 → 프레임워크 선정 후 방 캡슐화·시뮬레이션 루프부터.
- `RedisService`: 현재 `get/set/del`만 있음 → 레지스트리·heartbeat·결과 스트림(XADD/XREAD)·해시 등 확장 필요.
- `ThrottlerModule`: 인메모리 저장소 → **Redis 저장소로 교체**(다중 인스턴스 대비, §운영 전제).
- `server-match`: 인증 골격은 견고하나 **세션(Postgres)·계정상태·매치메이킹·결과 워커**가 신규로 필요. (기존 refresh=Redis 단일키 → sessions 테이블로 전환.)
- `user.service.ts`: 중복 가입 에러 처리 버그(`error.details` → `constraint_name`) 수정 필요.
- `client`: 타이틀 화면만. 로비/매칭 화면, Phaser 인게임, WS 네트워크 계층이 신규로 필요.

> 이 문서의 수치·프레임워크 선정 등은 확정 시 함께 갱신한다. 세부 미정 항목은 각 절의 **TBD** 참고.
