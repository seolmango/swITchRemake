## A. 지금 막고 있는 것

### A1. 결과 화면이 우승자 2명을 감당하지 못한다 — **codex 작업 중**

레이아웃이 우승자 1명을 전제로 짜여 있다. 실제 `winnerPlayerIds`는 **항상 길이 2**이고
(`[survivors[0] ?? 0, survivors[1] ?? survivors[0] ?? 0]`), 서로 다른 우승자 수는 0·1·2명 전부 나온다.
`0`은 playerId가 아니라 "없음" 자리표시자다(playerId는 1부터).

마지막 두 명이 같이 이기는 게 흔한 게임이니 **2명을 기본으로 두고** 설계한다.
참가자별 기록표도 지금은 작고 빽빽하다.

### A2. 글씨가 작아서 안 보인다 — **codex 작업 중**

타이틀 화면 외의 화면 — 설정, 도움말, 로비, 인게임 HUD — 이 전부 타이틀보다 한참 작고 얇다.
**인게임 스킬 아이콘이 특히 작다.**

기준은 타이틀 화면이다. 굵고 크고 동글동글하게, 여백도 같이 키운다.
팔레트(`client/src/theme/color.ts`)와 폰트(`--font-display` / `--font-ui`)는 그대로 두고
크기 체계만 통일한다. 같은 역할이면 화면이 달라도 같은 크기를 쓴다.

### A3. 엔진 제3자 검토 — **codex 작업 중**

인게임 문제가 반복해서 나온다. 카메라 떨림(`roundPixels`), out-of-memory(`setColor` 매 프레임),
맵 타임라인 미전송 — 전부 짜 놓은 사람이 못 보던 자리에 있었다. 밖에서 한 번 훑는다.
산출물은 `docs/reviews/ENGINE_REVIEW.md`. 코드는 고치지 않는다.

### A4. 브라우저 out-of-memory — **원인 미확정**

`setColor` 매 프레임 호출은 고쳤는데 사용자가 또 겪었다. 계측 결과(경기 약 100초, dpr 2, 1280x800):

| 지표 | 값 |
| --- | --- |
| texImage2D 호출 | 611회 (대부분 경기 시작 순간) |
| 업로드 누계 | 1.1 GB |
| createTexture / deleteTexture | 608 / 762 |
| JS 힙 | 26~52 MB로 안정 |

힙은 멀쩡하다. **JS 힙이 아니라 GPU/캔버스 쪽**이라는 뜻이다. 후보:
`SwitchEngine`의 `render: { preserveDrawingBuffer: true }`(스크린샷 도구용 편의값이다 — 제품 기능이 아니다),
dpr 2에서 2560x1600 백버퍼, 경기 시작 때 몰리는 텍스처 업로드. A3 검토 결과와 합쳐서 판정한다.

### A5. 클라이언트 자동 재접속 — **검증 대기**

구현은 들어갔다. 지수 백오프로 재시도하되 `isRetryable`이 false인 코드(AUTH_FAILED, KICKED,
ROOM_CLOSED)에는 재시도하지 않는다. 사용자 확인이 남았다.

## B. 게임을 완성하는 것

### B1. 사운드 — 오디오 시스템이 아예 없다

설정에 마스터·BGM·효과음 슬라이더가 있는데 `masterVolume`/`bgmVolume`/`sfxVolume`을 읽는 코드가
클라이언트에 한 줄도 없다. 재생 계층부터 만들어야 한다.

우선순위대로 — 이 다섯만 있어도 게임이 달라진다.

1. **태그 성사** — 잡히는 순간. 화면만으로는 늦다
2. **스킬 발동 3종** — 유체화(공기), 점멸(짧은 전자음), 탈진(둔탁하게 내려앉음)
3. **스위치 성공** — 태그와 명확히 구분되어야 한다
4. **스킬 실패** — 사거리 밖·쿨타임. 지금 화면 알림만 있다
5. **쿨타임 완료** — 작게

그 다음: 자기장 접근 경고(거리에 따라 강도), 맵 변화(벽 붕괴), 탈락(자기/남 구분),
카운트다운, 경기 종료. UI 효과음(클릭, 참가·퇴장, 이모지)과 BGM(로비·인게임·결과)은 마지막.

### B2. 스킬 아이콘

네 개가 **실루엣만으로 구분**되어야 한다(색각 이상 설정이 있다). 굵은 단일 선, 넉넉한 여백.

- **유체화** — 진행 방향으로 늘어난 물방울 + 짧은 잔상 두세 줄. 파랑
- **점멸** — 점선 윤곽(있던 자리) + 실선 형태(도착) + 사이 파선. **잔상 금지**(유체화와 가르는 지점). 보라
- **탈진** — 아래로 향하는 힘. 처진 어깨 + 하강 화살표. 나머지가 전부 수평이라 혼자 수직이면 즉시 구분. 낮은 채도
- **스위치** — 두 형태가 자리를 맞바꾸는 화살표 순환. 한쪽 원만 빨강(술래). 유일하게 주체가 둘이다

### B3. 통계 연결

결과는 DB에 쌓이는데(`users.stats`, `match_participants`) 읽는 경로가 없다.

- `GET /users/me/stats`, `GET /users/me/matches?limit&cursor` (둘 다 `@NeedAccount`)
- **shared 계약(Claude)**: 방 참가 명령에 `stats`를 실어 로비 카드의 전적을 살린다. 지금 항상 `null`이다
- `ProfilePage`의 "전적 API가 추가되면" 자리를 실제 값으로

### B4. 도움말 화면

`HowToPlayPage`가 정적 카드 4장이고 키를 `'W A S D'`로 하드코딩한다. 설정에서 키를 바꾼 사람에게 거짓말이다.

- **스킬 넷을 실제로 쓰는 모습을 애니메이션으로 보여준다.** 글로 설명하면 유체화와 점멸의 차이가 안 산다.
  `SwitchEngine`에 스크립트된 스냅샷을 먹이는 방식이면 데모와 실제가 어긋날 수 없다 —
  별도로 그린 그림은 밸런스를 고칠 때마다 조용히 거짓말이 된다
- 키 표시를 `keyBindings`에서 읽는다(`formatKeyBinding`이 이미 있다). 지금 `'W A S D'` 하드코딩은
  키를 바꾼 사람에게 거짓말이다
- reduced motion에서는 정지 프레임

### B5. 훈련장

지금 `/sandbox`는 클라이언트가 물리를 다시 구현한 764줄 목업이라 서버와 값이 이미 갈라져 있다.
**게임 서버의 방 모드로 만든다** — 로컬 실행은 네트워크 구간이 빠져 실제 경기와 감각이 달라진다.

- `mode: 'match' | 'training'`(shared 계약). 정원 1, 시작 잠금 없음, 결과를 outbox로 보내지 않음
- `barrier_speed = 0` 맵을 MapBuilder로 만든다 → 시뮬레이션 수정 없이 자기장이 멈춘다
- 봇은 `ResolvedInput`을 경로 추종기가 만들어 준다. **봇 로직은 `simulation/` 밖에**
- 특수 블록은 `TilePhysics`에 넣지 않는다(와이어 계약이 넓어진다). 훈련 맵 메타데이터의 패드 목록으로
  - **술래 변경 패드** — 밟으면 술래가 된다. 술래일 때의 감각을 연습할 방법이 지금 없다
  - **스킬 변경 패드** — 밟으면 로드아웃이 바뀐다. 로비로 나갔다 오지 않고 넷을 다 만져 볼 수 있어야 한다
- **봇은 아웃돼도 몇 초 뒤 되살아난다.** 한 번 잡고 나면 연습할 상대가 없어지는 게 지금 설계의 구멍이다
- **플레이어가 죽으면 관전자 모드로 넘어가고, 버튼을 누르면 다시 태어난다.**
  관전자 모드 자체도 연습 대상이다 — 실전에서 처음 겪으면 조작을 모른다
- **훈련장에서는 화면·사운드·인게임 설정을 실시간으로 바꿀 수 있다.** 인게임에서 막아 둔 것을
  여기서는 연다. 설정을 만져 보라고 있는 공간이다
- 완성되면 `/sandbox`는 지운다

## C. 품질과 도구

### C1. 브라우저 E2E 자동화

단위 테스트가 잡지 못하는 계층 사이 버그가 이 프로젝트의 주된 실패 유형이다.
Playwright로 첫 방문→가입→방 생성→코드 참가→로비→경기→F5 복구→결과→계정 삭제를 훑는다.
이메일은 sink(`test:mail:{to}`)로만 읽고 **실발송 0건**, 마지막에 결과 요약만 실제 SMTP로 한 통 보낸다.

**의존성 설치가 필요하므로 codex 샌드박스가 아니라 사람이 먼저 설치해야 한다.**

### C2. 리플레이 로컬 재생기

`shared`로 코덱을 옮겨 gzip/sha256을 주입받게 한 뒤(지금 `node:zlib`에 묶여 브라우저에서 못 돈다)
`/replay` 라우트에서 `.swr` 파일을 열어 `SwitchEngine`으로 재생한다. 파싱은 워커에서.

### C2-1. PWA와 저장 공간 — **결정 필요**

"리플레이·BGM을 PWA 설치자에게만 준다"는 아이디어가 나왔다. 근거가 된 전제 하나는 사실이 아니다.

- **설치해도 할당량은 안 늘어난다.** 저장 할당량은 origin 단위이고 남은 디스크에서 계산된다.
  설치 여부는 그 계산에 안 들어간다.
- **설치가 실제로 바꾸는 건 "안 지워지는 것"이다.** Chrome은 설치된 앱에
  `navigator.storage.persist()`를 자동 승인하는 쪽으로 기운다. Safari는 더 크다 —
  일반 사이트는 7일간 방문이 없으면 스크립트가 쓴 저장소를 통째로 지우는데, 홈 화면에 추가된
  웹앱은 그 대상에서 빠진다. iOS에서 리플레이를 보관하려면 사실상 설치가 필요하다.
- **BGM은 애초에 저장 공간 문제가 아니다.** 네트워크로 받아 HTTP 캐시에 얹으면 되는 몇 MB다.
  설치자에게만 소리를 준다는 건 게임의 절반을 잠그는 것에 가깝다.

그래서 제안: **막지 말고 늘려 준다.**

- 리플레이는 전원에게 준다. 보관 개수에 상한을 두고, 넘으면 오래된 것부터 지운다
- 시작할 때 `navigator.storage.persist()`를 부른다. 승인되면 상한을 올린다
- 거절됐을 때만 설치를 권한다 — "설치하면 리플레이가 안 지워져요". 잠금이 아니라 유인
- `navigator.storage.estimate()`로 남은 용량을 보여 준다. 사용자가 직접 판단할 수 있어야 한다

### C3. 클라이언트 점검

- ErrorBoundary는 들어갔다. 404가 무조건 `/`로 튕기는 것은 남아 있다
- 8인 풀방 + 연막에서 프레임 실측(지금까지 3인만 돌렸다)
- `client`에 테스트가 생겼지만(53개) 커버리지는 순수 함수 위주다

### C4. 테스트 정리 (C1 뒤에)

30여 개 파일에 300개 가까이 있다. 많은 편은 아니고, 일괄 삭감은 권하지 않는다.
**C1이 그물을 친 뒤에** 값이 낮은 것만 기준을 정해 줄인다.
`result.service.integration.spec.ts`가 DB opt-in이라 평소 안 돈다 — **안 도는 테스트가 제일 나쁘다.**

### C5. 문서 정리

## D. 마지막 점검 라운드 (R)

코드가 더 안 움직일 때. 찾을 것이 "스펙 위반"이 아니라 **"그럴듯한데 틀린 것"** 이라 마지막에 돈다.

- 티켓 검증의 원자적 소비와 실패 응답의 타이밍 차이
- Redis ACL 사용자 분리(지금은 단일 비밀번호)
- 세션 원본 IP의 보관 기간과 파기(`SESSION_IP_RETENTION_DAYS`가 실제로 도는지)
- **`ViolationSignal`의 `userId` 자리에 방 범위 `playerId`가 들어간다**(`GameSession`). 지금은 로그뿐이라
  무해하지만 제재 소비자가 붙는 순간 **엉뚱한 계정이 제재된다**
- **매칭 서버 다중 인스턴스에서 제어 응답을 남이 가져간다.** 소비자 그룹이 같아서, 다른 인스턴스가
  자기 `pending`에 없는 reply를 ACK하면 원 요청자는 2초 복구 타이머까지 기다린다.
  **수평 확장하는 순간 모든 방 생성이 2초가 된다**
- `game.emoji`의 `emojiId` 범위가 shared 계약에 없다(서버가 0..255로 막는 중)
- `JWT_GUEST_REFRESH_SECRET`이 없으면 `JWT_REFRESH_SECRET`으로 조용히 대체된다.
  `.env.example`은 둘이 달라야 한다고 명시하는데 코드가 그 규칙을 무력화한다
- 결정론 테스트와 가짜 클라이언트 부하 테스트
- 8인 풀방 tick 측정 후 프로세스당 방 수 상한 확정, `draining` 임계값
- outbox가 가득 찼을 때 신규 게임 시작 차단(지금은 로그만 남기고 전적이 유실된다)
- `replays`/`replay_holds` 보존·삭제 주기가 아무것도 안 돈다
