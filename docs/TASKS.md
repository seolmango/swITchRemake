## A. 지금 막고 있는 것

### A1. 인게임 새로고침이 자리를 잃는다 — **확인된 버그**

경기 중에 F5를 누르면 "이 방의 연결을 복구할 수 없습니다"에 갇힐 때가 있다. 매번은 아니다.

브라우저 자동 점검(`npm run e2e`)이 잡았고, Redis MONITOR로 순서까지 확인했다.

1. 새로고침으로 WebSocket이 끊긴다
2. **1초 안쪽에** 인게임 서버가 그 사람의 `user:{id}:active-room` 표를 지운다
   (`compareAndDelete`. 같은 순간 `room-rejoin` 쿨다운까지 같이 걸린다)
3. 매칭 서버의 `POST /rooms/:id/resume`이 `NO_ACTIVE_ROOM`으로 409를 돌려준다

표를 지우는 경로는 `registry.ts`의 `#synchronizeTrackedSeats` → `#flushPendingReleases`이고,
그 경로는 `room.hasUser(userId)`가 false일 때만 탄다. 그런데 `Room#disconnect`는
`RECONNECT_GRACE_MS`(10초) 동안 명단에 남겨 두기로 되어 있다. **둘 중 하나가 약속을 안 지킨다.**

점검은 `e2e/tests/07-match.spec.ts`에 `test.fixme`로 남겨 뒀다. 고치면 그 표시를 떼면 된다.

### A2. 이유 없이 로그아웃된다 — **둘 고쳤고, 뿌리 하나가 남았다**

"화면을 두어 번 옮기면 로그인이 풀린다"의 정체가 둘이었다. 자동 점검이 둘 다 잡았다.

**① 토큰 재발급이 두 번 동시에 나갔다.** refresh 토큰은 한 번 쓰면 회전하고, 서버는 이미 쓴
토큰이 다시 오면 재사용 공격으로 보고 **그 계정의 세션을 전부 끊는다**(`kind: 'reuse'`).
클라이언트에는 중복을 막는 guard가 있었지만 **401 재시도 경로만** 그것을 지났고, 화면을 새로
띄울 때 도는 `bootstrapApiIdentity`는 그냥 불렀다. 그래서 새 화면이 뜨는 순간 다른 요청이
401을 맞으면 둘이 같은 쿠키를 동시에 써서 정상 사용자가 로그아웃됐다.
→ 재발급을 종류별 single-flight 하나로 모았다(`client/src/api/http.ts`).

**② 거절당한 로그아웃이 화면만 로그아웃시켰다.** 진행 중인 방에 남아 있으면 서버가 로그아웃을
거절한다(`IDENTITY_SWITCH_DURING_ROOM`, 409). 그런데 스토어가 그 오류까지 삼키고 신원을
지워서, 화면은 "아직 로그인하지 않았어요"인데 서버에서는 여전히 로그인 상태였다. 사용자는
로그아웃된 줄 알고 자리를 뜨고 방은 그대로 남는다.
→ 409는 신원을 유지한 채 그대로 올려서 화면이 이유를 보여 줄 수 있게 했다.

탈퇴 직후에는 로그아웃을 아예 부르지 않는다(`abandonSession`). 계정이 이미 없어서 지울 세션도
없고, 방에 남아 있다는 이유로 409를 맞으면 탈퇴한 사람이 로그인 화면에 갇힌다.

**③ 남은 뿌리 — 회전이 화면 이동에 취약하다.** 둘을 고친 뒤에도 긴 점검에서는 여전히 로그아웃된다.
경기를 마치고 로비·방 목록·프로필로 빠르게 옮겨 다닐 때 나온다. 하나씩 돌리면 안 나고, 전체를
돌리면 난다.

지금 구조는 **화면을 새로 띄울 때마다** refresh 토큰을 회전시킨다. 회전 응답의 `Set-Cookie`가
브라우저에 반영되기 전에 다음 이동이 시작되면 브라우저는 **옛 토큰을 들고 간다.** 서버는 그것을
재사용으로 보고 그 계정의 세션을 전부 끊는다 — 정상 사용자가, 화면 두 번 옮겼다고.

흔한 완화책은 **직전 토큰을 짧은 유예(수 초) 동안 받아 주되 세션을 끊지는 않는 것**이다. 진짜
재사용(한참 뒤에 온 옛 토큰)은 그대로 막고, 경합만 걸러낸다. `auth.service.refresh`의
`kind: 'reuse'` 분기가 손댈 자리다.

점검은 이 상황을 만나면 "계정 세션이 사라졌습니다"로 분명히 말한다(`e2e/support/app.ts`의
`deleteAccount`). 정리 실패로 위장하지 않게 해 뒀다.

예전에 여기 있던 것들은 전부 끝났다 — 결과 화면 2인 우승(461cca6), UI 글씨 크기(461cca6),

**자동 재접속만 사용자 확인이 남았다.** 지수 백오프로 재시도하되 `isRetryable`이 false인

재접속이 붙어도 경기로 돌아가지 못하던 문제는 고쳤다 — `game.starting`/`game.started`가
시작하는 순간 한 번만 나가서, 도중에 들어온 연결은 방이 PLAYING인데도 "시작 신호를 기다리는"
화면에 갇혔다. 이제 방이 두 메시지를 보관했다가 붙는 연결에게 다시 보낸다.

## B. 게임을 완성하는 것

### B1. 사운드 — 오디오 시스템이 아예 없다

설정에 마스터·BGM·효과음 슬라이더가 있는데 `masterVolume`/`bgmVolume`/`sfxVolume`을 읽는 코드가
클라이언트에 한 줄도 없다. 재생 계층부터 만들어야 한다.

우선순위대로 — 이 다섯만 있어도 게임이 달라진다.

1. **태그 성사** — 잡히는 순간. 화면만으로는 늦다
2. **스킬 발동 3종** — 유체화(공기), 점멸(짧은 전자음), 탈진(둔탁하게 내려앉음)
3. **스위치 성공** — 태그와 명확히 구분되어야 한다
4. **스킬 실패** — 사거리 밖·쿨타임. 지금 화면 알림만 있다
5. **쿨타임 완료** — 작게

그 다음: 자기장 접근 경고(거리에 따라 강도), 맵 변화(벽 붕괴), 탈락(자기/남 구분),
카운트다운, 경기 종료. UI 효과음(클릭, 참가·퇴장, 이모지)과 BGM(로비·인게임·결과)은 마지막.

### B2. 스킬 아이콘 — **완료**

아이콘은 `client/src/assets/images/skill_*.svg`에 있다. 아래는 설계 근거로 남긴다.

**이름은 롤 소환사 주문에서 왔다** — 유체화(Ghost) / 점멸(Flash) / 탈진(Exhaust).
스위치만 이 게임 고유다. 코드 id(`SkillId`의 `dash`/`flash`/`exhaust`/`switch`)는 와이어 계약이라
바꾸지 않고 **표시 이름만** 맞춘다 — id를 바꾸면 리플레이 파일에 박힌 값까지 따라와야 한다.
화면 이름의 유일한 출처는 로케일의 `lobby.skills.*` 하나다.

한동안 `dash`가 코드에서는 dash, 주석에서는 유체화, 화면에서는 "대시"로 세 갈래였고
그 탓에 도움말에 없는 스킬이 하나 생겼다(2026-08-25에 정리).

네 개가 **실루엣만으로 구분**되어야 한다(색각 이상 설정이 있다). 굵은 단일 선, 넉넉한 여백.

- **유체화** — 진행 방향으로 늘어난 물방울 + 짧은 잔상 두세 줄. 파랑
- **점멸** — 점선 윤곽(있던 자리) + 실선 형태(도착) + 사이 파선. **잔상 금지**(유체화와 가르는 지점). 보라
- **탈진** — 아래로 향하는 힘. 처진 어깨 + 하강 화살표. 나머지가 전부 수평이라 혼자 수직이면 즉시 구분. 낮은 채도
- **스위치** — 두 형태가 자리를 맞바꾸는 화살표 순환. 한쪽 원만 빨강(술래). 유일하게 주체가 둘이다

### B3. 통계 연결 — **완료**

끝났다. `GET /users/me/stats`와 `GET /users/me/matches`가 붙었고(9bcd4d9), `ProfilePage`가
그것을 읽는다. 로비 카드의 전적도 매칭 서버가 자리 예약에 실어 보내는 것으로 살렸다(0883e43).

레벨·XP도 붙었다(9c6f9a9). 레벨은 저장하지 않고 누적 XP에서 센다 — 수치는
`shared/src/protocol/progression.ts`의 `PROGRESSION`에 모여 있다.

XP는 **참가·승리·태그·스위치 성공·생존시간** 다섯 항목이다. 생존은 1분당 12점을 초 단위로
비례해서 주고 10분에서 끊는다(자기장이 멈춘 방에서 가만히 서 있는 것이 최고 효율이 되면 안 된다).
결과 화면이 그 내역을 그대로 줄 세워 보여 준다 — 총합만 보이면 무엇을 더 해야 하는지 알 수 없다.

### B4. 도움말 화면 — **완료**

게임 룰 / 조작키 / 술래 / 스킬 / 훈련장 순으로 다시 짰다. 키는 `keyBindings`에서 읽고,

### B5. 훈련장 — **대부분 완료**

게임 서버의 방 모드(`RoomMode.Training`)로 만들었다. 클라이언트가 물리를 다시 구현하던
`/sandbox` 목업은 지웠다 — 서버와 값이 갈라지는 것이 그 설계의 문제였다.

되어 있는 것:

- 혼자 시작, 자기장 정지, 스스로 끝나지 않음, 결과 안 내보냄, 방 목록에 안 뜸
- 훈련장 맵은 경기 방의 맵 목록과 `random` 추첨에서 빠진다(`training_only`, 번들 스키마 3)
- 전용 맵(40x40)과 구역: 정지 표적 / 순찰 표적 / 추격 구역 / 스킬 패드 열
- 패드 여섯(유체화·점멸·탈진·초기화·술래·추격모드). **맵 마커 레이어**로 만들었고
  나중에 인게임 특수 타일(포탈·쿨감)도 같은 레이어에 얹힌다. 패드는 별도 메시지가 아니라
  맵 번들에서 온다 — 클라이언트가 이미 같은 번들을 해시 검증해서 받는다
- 표적은 경로 추종기가 `ResolvedInput`을 만들어 준다. 그래서 탈진을 걸면 실제로 느려진다
- 잡힌 표적은 3초 뒤 부활. 사람은 죽으면 관전 후 버튼으로 부활
- 플레이 중 설정 변경

남은 것:

- **봇 술래 고도화.** 지금은 직진 추적이라 벽에 걸린다. 게임이 안정되면 손본다(사용자 결정)

### B6. 운영자 페이지 — **대시보드만 완료**

`/admin`. 관리자 계정으로 로그인하면 홈 화면 오른쪽 아래에 방패 버튼이 생긴다.

지금 보이는 것 — 인게임 접속 수, 방(대기/진행/상한), 인게임 서버 목록(방 수·접속·루프 지연·
버전·draining), 매칭 서버 목록(분당 요청·대기 명령), 활성 계정·세션·오늘 가입, 최근 1시간/24시간
경기와 미기록 경기. 4초마다 갱신하고 끌 수 있다.

설계에서 지킨 것:

- **역할은 토큰에 안 싣는다.** 요청마다 DB에서 읽는다 — 강등된 사람이 토큰 수명만큼 관리자로
  남으면 안 된다. `users.role`은 `USER`/`ADMIN` enum이고 나중에 support/moderator/security를
  덧붙일 수 있다(`FUTURE.md` §3.1)
- 첫 관리자는 화면에서 만들 수 없다. `npm run admin:grant -- <email>` (`--revoke`로 회수)
- 대시보드에는 **집계만** 있다. IP·닉네임·계정 ID는 오지 않는다 — 플레이어 조회는 별도 권한과
  감사 로그를 요구하는 화면이고, 대시보드에 슬쩍 얹으면 그 통제가 무의미해진다
- Redis가 죽어도 DB 숫자는 낸다. 장애 중에 화면이 통째로 비면 정작 필요할 때 아무것도 못 본다

매칭 서버도 이제 자기 상태를 heartbeat로 알린다(`MatchServerHeartbeat`). 분당 요청 수는 프로세스
안에서 초 단위 링버퍼로 세고 2초마다 한 번만 Redis에 쓴다 — 요청마다 Redis를 두드리면 측정이
곧 부하가 되고, 바쁠수록 측정 비용도 같이 는다.

남은 것 — 신고 큐, 플레이어 조회, 제재 관리, 감사 로그 열람. 전부 신고 기능이 먼저다.

- 화면 요소는 **로케일 파일의 문구**로 찾는다. 문구를 고치면 점검이 같이 따라온다
- 인증 코드는 sink(`test:mail:{to}`)로만 읽는다. **실발송 0건**

- 흐름마다 끝에서 스스로 탈퇴하고, 남은 것은 teardown이 치운다(`npm run e2e:cleanup`)

**잡은 것** — A1(인게임 새로고침, 미해결), A2(로그아웃 원인 셋 중 둘 고침, 뿌리 하나 남음). 그 밖에 이 과정에서
드러나 고친 것: 강퇴당한 사람이 이유 없이 갇히던 것, 오류 문구가 입력칸의 접근성 이름을
오염시키던 것, 가입·재설정 안내가 로그인 화면에서 사라지던 것, 탈퇴 화면과 비밀번호 재설정
API가 아예 없던 것.

한도 완화 플래그가 하나 필요하다 — `RATE_LIMIT_RELAXED=true`. 한 IP에서 수십 개 계정을 만들고
지우는데 `/auth/verify`가 IP당 분당 5회라 그대로는 끝까지 못 돈다. 가드는 그대로 돌고 한도만
50배가 된다. `APP_ENV=prod`면 서버가 부팅을 거부한다.

### C2-1. PWA와 저장 공간 — **결정 필요**

"리플레이·BGM을 PWA 설치자에게만 준다"는 아이디어가 나왔다. 근거가 된 전제 하나는 사실이 아니다.

- **설치해도 할당량은 안 늘어난다.** 저장 할당량은 origin 단위이고 남은 디스크에서 계산된다.
  설치 여부는 그 계산에 안 들어간다.
- **설치가 실제로 바꾸는 건 "안 지워지는 것"이다.** Chrome은 설치된 앱에
  `navigator.storage.persist()`를 자동 승인하는 쪽으로 기운다. Safari는 더 크다 —
  일반 사이트는 7일간 방문이 없으면 스크립트가 쓴 저장소를 통째로 지우는데, 홈 화면에 추가된
  웹앱은 그 대상에서 빠진다. iOS에서 리플레이를 보관하려면 사실상 설치가 필요하다.
- **BGM은 애초에 저장 공간 문제가 아니다.** 네트워크로 받아 HTTP 캐시에 얹으면 되는 몇 MB다.
  설치자에게만 소리를 준다는 건 게임의 절반을 잠그는 것에 가깝다.

그래서 제안: **막지 말고 늘려 준다.**

- 리플레이는 전원에게 준다. 보관 개수에 상한을 두고, 넘으면 오래된 것부터 지운다
- 시작할 때 `navigator.storage.persist()`를 부른다. 승인되면 상한을 올린다
- 거절됐을 때만 설치를 권한다 — "설치하면 리플레이가 안 지워져요". 잠금이 아니라 유인
- `navigator.storage.estimate()`로 남은 용량을 보여 준다. 사용자가 직접 판단할 수 있어야 한다

## D. 마지막 점검 라운드 (R)

코드가 더 안 움직일 때. 찾을 것이 "스펙 위반"이 아니라 **"그럴듯한데 틀린 것"** 이라 마지막에 돈다.

- 티켓 검증의 원자적 소비와 실패 응답의 타이밍 차이
- Redis ACL 사용자 분리(지금은 단일 비밀번호)
- 세션 원본 IP의 보관 기간과 파기(`SESSION_IP_RETENTION_DAYS`가 실제로 도는지)
- **매칭 서버 다중 인스턴스에서 제어 응답을 남이 가져간다.** 소비자 그룹이 같아서, 다른 인스턴스가
  자기 `pending`에 없는 reply를 ACK하면 원 요청자는 2초 복구 타이머까지 기다린다.
  **수평 확장하는 순간 모든 방 생성이 2초가 된다**
- `game.emoji`의 `emojiId` 범위가 shared 계약에 없다(서버가 0..255로 막는 중)
- 가짜 클라이언트 부하 테스트 (결정론 테스트는 `simulation/determinism.test.ts`로 들어갔다)
- 8인 풀방 tick 측정 후 프로세스당 방 수 상한 확정, `draining` 임계값
- `replays`/`replay_holds` 보존·삭제 주기가 아무것도 안 돈다

## 부록: 로컬 실행

```bash
npm run db:up
npm run build
npm run match:dev      # 3000
npm run game:start     # 4000
npm run dev -w client  # 5173
```

같은 `GAME_SERVER_ID`로 두 번 띄우면 기동을 거부한다(명령 스트림이 갈리는 것을 막는다).

`game:start` 대신 `npm run cluster:start`를 쓰면 게이트웨이(4100)와 감독자가 뜨고, 인게임
서버는 감독자가 부하를 보고 알아서 띄운다. 실제로 돌아가는 모양은 이쪽이다.

브라우저 자동 점검:

```bash
npx playwright install chromium   # 최초 1회
npm run e2e                       # 서버가 안 떠 있으면 알아서 띄운다
npm run e2e -- --headed           # 무엇을 하는지 보면서
npm run e2e:report                # 실패한 흐름의 화면·트레이스
npm run e2e:cleanup -- --apply    # 점검이 남긴 계정 정리
```

매칭 서버를 직접 띄워 두고 점검을 돌린다면 `RATE_LIMIT_RELAXED=true`를 붙여야 한다.
안 그러면 인증 메일 한도(IP당 분당 5회)에 걸려 중간부터 전부 실패한다.

관리자 계정: `npm run admin:grant -- <email>` (회수는 `-- <email> --revoke`).
