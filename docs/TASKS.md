## B. 게임을 완성하는 것

### B1. 사운드 — **재생 계층 완료. 소리 자체는 임시**

`client/src/audio/`에 붙었다. 슬라이더 세 개가 실제로 그래프의 gain 노드 셋을 움직이고,
아래 목록의 소리가 전부 난다. **남은 것은 음원 교체뿐이다** — 지금 들어 있는 18개는
`scripts/build-audio.cjs`가 사인파와 노이즈로 합성한 자리 채우기다.

    client/src/audio/AudioBus.ts       그래프 하나. sfxGain·bgmGain → masterGain → destination
                    sfxPlayer.ts       첫 제스처에 전부 받아 디코드. AudioBuffer로 들고 있는다
                    bgmPlayer.ts       사용자가 켤 때만 받는다. Cache Storage + <audio> 스트리밍
                    matchSfx.ts        "언제 울리는가"의 유일한 출처
                    manifest.generated.ts   빌드 산출물. 손대지 말 것

**소리를 바꾸려면** `client/public/audio/sfx/<id>.mp3`를 덮어쓰고 `npm run audio:build -- --sfx-skip`.
파일 이름이 계약이고, 그 명령은 바이트 수만 다시 잰다. **BGM을 바꾸려면**
`client/src/assets/swITchover.{wav,mp3}`를 갈고 `npm run audio:build`.

우선순위대로 — 이 다섯이 게임을 바꾼다고 봤고, 전부 붙었다.

1. **태그 성사** — 스냅샷의 술래 교체에서. 화면보다 먼저 도착한다
2. **스킬 발동 3종** — 유체화(스냅샷 이펙트), 점멸(`player.blinked`), 탈진(`player.skillArea`)
3. **스위치 성공** — `player.skillArea`. 뒤따르는 술래 교체는 태그로 치지 않는다
4. **스킬 실패** — `skill.rejected`
5. **쿨타임 완료** — 스냅샷 쿨타임이 0으로 떨어지는 순간. 작게

그 다음 층도 들어갔다: 자기장 접근 경고(경계까지 두 칸 반 안, 거리로 볼륨),
맵 변화(`tileChanges`), 탈락(자기/남 구분 — `player.eliminated`), 카운트다운, 경기 종료.
UI는 클릭(`RoundButton`), 참가·퇴장(로비 인원 변화), 이모지(스냅샷 `emojiId`).

**서버 프로토콜은 한 글자도 안 늘었다.** 이미 보내던 것들의 변화 지점에서 소리를 만든다.
그래서 시야 모델도 저절로 지켜진다 — 안 보이는 사람은 스냅샷에 없고, 없으면 소리도 없다.
`player.eliminated`만 새로 구독한다(스냅샷에서는 "시야에서 사라짐"과 구분이 안 된다).

#### BGM과 트래픽 — 왜 켤 때 받는가

효과음은 다 합쳐 100KB라 묻지 않고 받는다. BGM은 1MB고, 그래서 **기본값이 꺼짐이다.**
설정에서 켤 때 받고, 받은 것은 Cache Storage에 넣는다. 두 번째 접속부터 네트워크는 0이다.

HTTP 캐시만으로도 대개는 된다(파일 이름에 내용 해시가 있으니 `immutable`을 걸 수 있다).
Cache Storage를 쓰는 이유는 **브라우저가 HTTP 캐시를 말없이 비우기 때문**이다. 사용자가
"받기"를 눌러 1MB를 쓴 이상, 그게 살아 있는지 우리가 물어볼 수 있어야 하고 지울 수도 있어야 한다.

배포에서 반드시 걸 것 — 이게 실제 트래픽 절감이다:

    /audio/bgm/*   Cache-Control: public, max-age=31536000, immutable
    /audio/sfx/*   Cache-Control: public, max-age=604800

BGM은 이름에 해시가 있으니 `immutable`이 안전하다. 효과음은 이름이 고정(교체 계약)이라
1년은 못 건다. 둘 다 이미 압축돼 있으므로 전송 압축(gzip/br)은 꺼야 한다 — 커지기만 한다.

유튜브 임베드를 숨겨서 재생하던 방식은 버렸다. 약관 문제를 빼도 볼륨 슬라이더가 안 걸리고,
자동재생 정책에 막히고, 광고가 끼고, 트래픽이 오히려 더 든다.

남은 판단 두 가지:

- **마스터가 아직 mp3다**(64kbps·24kHz). 원본 wav를 `client/src/assets/`에 두고 다시 돌리면
  같은 용량에서 더 낫다. 손실 위에 손실을 얹지 않게 된다
- **곡을 짧게 끊어 루프시키면 용량이 절반이다**(현재 2분 33초). 이건 인코딩이 아니라
  작곡 쪽 결정이라 사용자 몫으로 남긴다

### B2. 스킬 아이콘 — **완료**

아이콘은 `client/src/assets/images/skill_*.svg`에 있다. 아래는 설계 근거로 남긴다.

**이름은 롤 소환사 주문에서 왔다** — 유체화(Ghost) / 점멸(Flash) / 탈진(Exhaust).
스위치만 이 게임 고유다. 코드 id(`SkillId`의 `dash`/`flash`/`exhaust`/`switch`)는 와이어 계약이라
바꾸지 않고 **표시 이름만** 맞춘다 — id를 바꾸면 리플레이 파일에 박힌 값까지 따라와야 한다.
화면 이름의 유일한 출처는 로케일의 `lobby.skills.*` 하나다.

한동안 `dash`가 코드에서는 dash, 주석에서는 유체화, 화면에서는 "대시"로 세 갈래였고
그 탓에 도움말에 없는 스킬이 하나 생겼다(2026-08-25에 정리).

네 개가 **실루엣만으로 구분**되어야 한다(색각 이상 설정이 있다). 굵은 단일 선, 넉넉한 여백.

- **유체화** — 진행 방향으로 늘어난 물방울 + 짧은 잔상 두세 줄. 파랑
- **점멸** — 점선 윤곽(있던 자리) + 실선 형태(도착) + 사이 파선. **잔상 금지**(유체화와 가르는 지점). 보라
- **탈진** — 아래로 향하는 힘. 처진 어깨 + 하강 화살표. 나머지가 전부 수평이라 혼자 수직이면 즉시 구분. 낮은 채도
- **스위치** — 두 형태가 자리를 맞바꾸는 화살표 순환. 한쪽 원만 빨강(술래). 유일하게 주체가 둘이다

### B6. 운영자 페이지 — **대시보드만 완료**

`/admin`. 관리자 계정으로 로그인하면 홈 화면 오른쪽 아래에 방패 버튼이 생긴다.

지금 보이는 것 — 인게임 접속 수, 방(대기/진행/상한), 인게임 서버 목록(방 수·접속·루프 지연·
버전·draining), 매칭 서버 목록(분당 요청·대기 명령), 활성 계정·세션·오늘 가입, 최근 1시간/24시간
경기와 미기록 경기. 4초마다 갱신하고 끌 수 있다.

설계에서 지킨 것:

- **역할은 토큰에 안 싣는다.** 요청마다 DB에서 읽는다 — 강등된 사람이 토큰 수명만큼 관리자로
  남으면 안 된다. `users.role`은 `USER`/`ADMIN` enum이고 나중에 support/moderator/security를
  덧붙일 수 있다(`FUTURE.md` §3.1)
- 첫 관리자는 화면에서 만들 수 없다. `npm run admin:grant -- <email>` (`--revoke`로 회수)
- 대시보드에는 **집계만** 있다. IP·닉네임·계정 ID는 오지 않는다 — 플레이어 조회는 별도 권한과
  감사 로그를 요구하는 화면이고, 대시보드에 슬쩍 얹으면 그 통제가 무의미해진다
- Redis가 죽어도 DB 숫자는 낸다. 장애 중에 화면이 통째로 비면 정작 필요할 때 아무것도 못 본다

매칭 서버도 이제 자기 상태를 heartbeat로 알린다(`MatchServerHeartbeat`). 분당 요청 수는 프로세스
안에서 초 단위 링버퍼로 세고 2초마다 한 번만 Redis에 쓴다 — 요청마다 Redis를 두드리면 측정이
곧 부하가 되고, 바쁠수록 측정 비용도 같이 는다.

**신고는 서버까지 됐다.** 경기 하나·대상 하나를 사건으로 묶고(`moderation_cases`), 게스트도
대상이 된다(계정 대신 경기 안의 자리로 가리킨다). 신고가 들어오면 그 경기 리플레이에 hold를
걸어 보관 정리에서 뺀다. 운영자는 큐를 보고 상태를 옮기거나 제재를 건다 — 제재는 기존
`SanctionService`를 그대로 쓰고, 걸면 사건이 ACTIONED로 간다. **게스트 사건에는 제재를 걸 수
없다**(400). 계정이 없으면 걸 곳이 없다.

신고 창은 날짜가 아니라 **리플레이 수명**이다. 증거가 사라진 뒤에 접수만 받아 두면 조사할 수
없다. 리플레이 기록이 아예 없는 경기는 보관 기간만큼 받는다 — 그러지 않으면 방금 끝난 경기의
신고 버튼이 죽는다.

화면도 붙었다. 결과 화면의 각 줄에 신고가 있고(자기 줄과 게스트 시야에는 없다), 운영자는
`/admin`의 신고 탭에서 큐를 보고 상태를 옮기거나 제재를 건다. 보관 기간은 서버가 내려 주는
값으로 화면에 적는다.

남은 것 — 신고 흐름 e2e, 플레이어 조회, 감사 로그 열람.

지금 안 만든 것과 이유 — 관전 화면 신고와 운영자 즉시 강퇴(라이브 대응)는 운영자가 마침
접속해 있어야 성립하고 경기가 5분 안팎이라 창이 짧다. 신고가 실제로 쌓이기 시작하면 붙인다.
신고 N건에 자동 강퇴는 **하지 않는다** — 셋이 짜면 한 명을 몰아낼 수 있고, 그건 치터보다
흔한 악용이다. 자동 규칙은 큐 정렬 가중치까지만 쓴다.

### C1. 브라우저 E2E 자동화 — **완료**

`e2e/`에 Playwright로 붙였다. `npm run e2e`. 자세한 것은 `e2e/README.md`.

11개 묶음 30여 개 흐름 — 첫 방문·가입·로그인·로그아웃·비밀번호 찾기·비밀번호 변경·프로필·
전적·로그인 기기·방 생성·목록·코드 참가·비공개 방·대기실(맵/잠금/스킬/강퇴/방장 넘기기)·
경기·도중 이탈·결과·XP·훈련장·설정·도움말·운영자 화면·탈퇴.

- 화면 요소는 **로케일 파일의 문구**로 찾는다. 문구를 고치면 점검이 같이 따라온다
- 인증 코드는 sink(`test:mail:{to}`)로만 읽는다. **실발송 0건**
- 마지막에 표 하나만 찍는다(`e2e/support/summary-reporter.ts`). 실패한 흐름만 이유가 붙는다
- 흐름마다 끝에서 스스로 탈퇴하고, 남은 것은 teardown이 치운다(`npm run e2e:cleanup`)

**잡은 것** — A1과 A2. 둘 다 고쳤다(a8830f0, b498df3). 그 밖에 이 과정에서
드러나 고친 것: 강퇴당한 사람이 이유 없이 갇히던 것, 오류 문구가 입력칸의 접근성 이름을
오염시키던 것, 가입·재설정 안내가 로그인 화면에서 사라지던 것, 탈퇴 화면과 비밀번호 재설정
API가 아예 없던 것.

한도 완화 플래그가 하나 필요하다 — `RATE_LIMIT_RELAXED=true`. 한 IP에서 수십 개 계정을 만들고
지우는데 `/auth/verify`가 IP당 분당 5회라 그대로는 끝까지 못 돈다. 가드는 그대로 돌고 한도만
50배가 된다. `APP_ENV=prod`면 서버가 부팅을 거부한다.

### C2. 리플레이 로컬 재생기 — **완료**

`/replay`. 파일을 놓으면 그 자리에서 재생한다. 서버도 로그인도 필요 없어서, 개발하는
사람끼리 `.swrp`를 주고받으면 그대로 같은 장면을 본다.

코덱은 `shared`로 옮기고 gzip·sha256을 주입받는다. 노드는 zlib·crypto, 브라우저는
`DecompressionStream`·`crypto.subtle`이다. 브라우저 쪽이 비동기라 압축·해시를 건드리는
셋은 비동기가 됐지만, 헤더만 읽는 `parseReplayContainer`는 동기로 남겼다 — 파일을 열자마자
무엇인지 보여 주는 경로에 await가 끼면 화면이 한 박자 늦는다.

**서명은 컨테이너 끝에 트레일러로 붙인다**(`keyId` + Ed25519 서명 + `"SWSG"`). manifest
안에 넣으면 "서명을 뺀 manifest"를 다시 만들어야 하고, 그 순간 JSON 표기 방식이 검증의
일부가 된다. 뒤에 붙이면 서명 대상이 "앞의 바이트 전부"로 단순해지고 옛 파서도 그대로 읽는다.

검증은 네 갈래다. 서명이 **없는 것**과 **모르는 키**는 둘 다 "확인할 수 없음"이다 — 사실
진술이지 경고가 아니다. 키를 바꾼 다음 날 멀쩡한 옛 파일이 전부 경고를 달면 그 표시는 곧
무시된다. 해시가 이미 깨졌으면 서명은 보지 않는다.

개인키는 인게임 서버가 env로 든다(`npm run replay:keygen`). **타협이다** — `FUTURE.md` §8은
signer service나 KMS를 쓰라고 한다. 옮길 때 고칠 곳은 `replay/signing.ts` 하나다.

남은 것 — 플레이어가 자기 경기를 내려받는 경로. 리플레이는 인게임 서버 디스크에 있고
받아갈 길이 없다. 보관이 7일·50경기라 "보고 싶으면 지금 저장해 두라"는 안내가 함께 가야 한다.
### C2-1. PWA와 저장 공간 — **결정 필요**

"리플레이·BGM을 PWA 설치자에게만 준다"는 아이디어가 나왔다. 근거가 된 전제 하나는 사실이 아니다.

- **설치해도 할당량은 안 늘어난다.** 저장 할당량은 origin 단위이고 남은 디스크에서 계산된다.
  설치 여부는 그 계산에 안 들어간다.
- **설치가 실제로 바꾸는 건 "안 지워지는 것"이다.** Chrome은 설치된 앱에
  `navigator.storage.persist()`를 자동 승인하는 쪽으로 기운다. Safari는 더 크다 —
  일반 사이트는 7일간 방문이 없으면 스크립트가 쓴 저장소를 통째로 지우는데, 홈 화면에 추가된
  웹앱은 그 대상에서 빠진다. iOS에서 리플레이를 보관하려면 사실상 설치가 필요하다.
- **BGM은 애초에 저장 공간 문제가 아니다.** 네트워크로 받아 HTTP 캐시에 얹으면 되는 몇 MB다.
  설치자에게만 소리를 준다는 건 게임의 절반을 잠그는 것에 가깝다.

그래서 제안: **막지 말고 늘려 준다.**

- 리플레이는 전원에게 준다. 보관 개수에 상한을 두고, 넘으면 오래된 것부터 지운다
- 시작할 때 `navigator.storage.persist()`를 부른다. 승인되면 상한을 올린다
- 거절됐을 때만 설치를 권한다 — "설치하면 리플레이가 안 지워져요". 잠금이 아니라 유인
- `navigator.storage.estimate()`로 남은 용량을 보여 준다. 사용자가 직접 판단할 수 있어야 한다
