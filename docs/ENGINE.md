# swITch 인게임 엔진 설계

렌더링 엔진(`client/src/game/`)의 구조, 3가지 모드, 서버 바이너리 프로토콜 정의.

---

## 1. 대원칙: 모든 판정은 서버

엔진은 **판정하지 않는다.** 누가 숨었는지, 누가 누구를 볼 수 있는지, 수풀이 얼마나 비치는지를 엔진이 계산하는 코드는 존재하지 않는다. 엔진은 서버가 내려준 결과만 그린다.

| 사실 | 누가 정하나 | 엔진이 받는 형태 |
|---|---|---|
| 이 플레이어가 보이는가 | 서버 | **아예 안 보내면 안 보임.** 엔진에 스폰조차 안 됨 |
| 보이지만 수풀 속인가 | 서버 | 플레이어당 `obscured` 플래그 1비트 → 반투명(0.6)으로 그림 |
| 이 수풀 타일이 얼마나 비치나 | 서버 | 타일별 알파값. 안 보낸 타일은 불투명 |
| 자기장 범위 | 서버 | 사각형 좌표 |
| 이펙트 잔여시간 | 서버 | 비율 1바이트 |

**줌만 예외적으로 클라이언트 소유.** 유저가 클라이언트를 뜯어 줌아웃해도 얻을 게 없다 — 보면 안 되는 플레이어는 애초에 패킷에 없기 때문. 그래서 줌은 서버 왕복 없이 즉각 반응하게 두는 편이 낫다.

### 이게 왜 중요한가

레거시(레거시 `RenderingManager.js:285-327`)는 클라이언트가 벽 모서리 기하 계산으로 은신 여부를 직접 판정했다. 즉 **모든 플레이어 좌표가 클라이언트에 이미 도착해 있었다** — 렌더링만 안 했을 뿐이라 메모리를 뜯으면 전부 보였다. 이번 설계는 그 구조적 취약점을 없앤다.

## 2. 3가지 모드

엔진은 하나지만 진입 모드가 3개다.

| 모드 | 자기 자신 | 카메라 | 입력 | 데이터 출처 |
|---|---|---|---|---|
| `play` | 있음 | 자기 자신 팔로우 (자유시점 전환 가능) | 이동 + 스킬 + 이모지 | 서버 소켓 |
| `spectate` | 없음 | 자유시점 / 아무나 팔로우 | 카메라 조작만 | 서버 소켓 (관전자용, 은신 검열 없음) |
| `help` | 있음(가상) | 스크립트가 지정 | 튜토리얼이 허용한 것만 | **로컬 스크립트** (서버 없음) |

`help` 모드가 서버 없이 도는 게 핵심이다. 튜토리얼은 같은 엔진에 같은 형식의 스냅샷을 로컬에서 만들어 먹인다 — 즉 **튜토리얼 스크립트 = 미니 서버**. 덕분에 튜토리얼 전용 렌더링 분기가 필요 없다.

관전 모드는 서버가 은신 검열을 하지 않은 스냅샷을 보낸다(관전자는 다 봐도 됨). 프로토콜은 동일하고, 서버가 채우는 내용만 다르다.

## 3. React ↔ Phaser 경계

레거시는 UI까지 캔버스에 그렸다(`UIctx`). 이번엔 나눈다. 기준은 **화면 고정이냐 월드 고정이냐** 하나뿐이다.

### Phaser (월드 고정 — 플레이어와 함께 움직이고 줌에 따라 커짐)
- 맵, 벽, 수풀, 연막, 자기장
- 플레이어 본체 / 술래 링 / 이펙트 링
- 지속시간 바, 번호/닉네임 라벨
- **머리 위 이모지**

### React (화면 고정 HUD — 줌과 무관하게 항상 같은 크기)
- 플레이어 목록 사이드바 (레거시 377-388)
- 생존자 수 (388)
- 스킬 버튼 + 쿨다운 (390-396)
- **이모지 선택 휠** (404-425) — 레거시는 화면 중앙 원형 배치였는데, CSS `transform: rotate()`로 훨씬 쉽게 만들 수 있고 키보드 접근성도 공짜로 얻는다
- 알림/토스트 (30)
- 모든 메뉴/로비

이모지만 양쪽에 걸친다: **선택 UI는 React, 머리 위 표시는 Phaser.**

### 하나로 묶기

페이지가 Phaser와 HUD를 따로 조립하면 상태 동기화가 양쪽으로 갈라져 관리가 어려워진다. 그래서 외부에 노출하는 건 컴포넌트 하나뿐이다.

```tsx
<SwitchGame mode="play" source={socketSource} />
```

```
<SwitchGame>                     ← 페이지가 마운트하는 유일한 것
  ├── <GameCanvas>               Phaser 월드. SwitchEngine 소유
  └── <GameHud>                  position:absolute 오버레이
       └── (모드에 따라 다른 HUD)
```

`SwitchGame`이 엔진 인스턴스를 소유하고, 스냅샷을 받아 엔진에 먹이고, HUD가 필요한 것(내 쿨다운, 생존자 수 등)만 React state로 끌어올린다. HUD의 클릭(스킬 사용, 이모지 선택)은 `SwitchGame`을 통해 서버로 나간다. 페이지는 모드와 데이터 소스만 정하면 된다.

**HUD로 끌어올리는 상태는 최소로.** 플레이어 좌표처럼 매 틱 바뀌는 값을 React state에 넣으면 초당 수십 번 리렌더가 돈다. 좌표는 엔진 안에서만 흐르고, HUD는 쿨다운·생존자수처럼 사람이 읽는 저빈도 값만 구독한다.

## 4. 바이너리 프로토콜

### 왜 바이너리이고, 왜 엔진이 직접 파싱하나

JSON으로 같은 내용을 보내면 3~5배 커진다. 그리고 파싱을 페이지 코드가 맡으면 "서버 형식 → 엔진 API" 변환 코드가 모드마다 중복된다. 엔진이 직접 먹으면 그 변환이 한 곳에만 존재한다.

```ts
engine.applySnapshot(arrayBuffer);   // 이게 전부
```

### 공통 규약

이 형식의 encoder/decoder는 `shared/src/protocol/snapshot.ts` 한 곳에만 있다. 서버 송신, 개발
샌드박스, 튜토리얼, 리플레이 기록이 모두 같은 함수를 쓴다.

- **리틀 엔디언**
- 좌표: 월드 px, `u16` — 최대 65535px = 255타일. 현재 최대 맵 50타일(12800px)이라 여유 충분하고 1px 정밀도
- 타일 좌표: `u8` (맵 255×255까지)
- 플레이어 id: `u8`
- 비율/알파: `u8` (0~255 → 0.0~1.0)

### 헤더 (6바이트)

| 오프셋 | 타입 | 내용 |
|---|---|---|
| 0 | u8 | `version` — 현재 2 |
| 1 | u8 | `flags` — bit0: 1이면 풀 스냅샷, 0이면 델타 |
| 2 | u32 | `tick` |

`tick`은 `u32`다. `u16`이면 60Hz에서 약 18분마다 한 바퀴 도는데, 그때마다 wrap을 고려한 비교가
필요해진다. 2바이트를 아끼는 것보다 그 버그가 안 생기는 쪽이 낫다. 입력 패킷의 `inputSequence`는
`u16`을 유지하고 `shared`의 wrap 비교 함수를 쓴다 — 그쪽은 매 틱 나가는 값이라 크기가 실제로 의미 있다.

### 섹션

헤더 뒤에 섹션이 버퍼 끝까지 반복된다. 모르는 `type`은 `length`만큼 건너뛴다 — **서버가 신기능을 추가해도 구버전 클라이언트가 죽지 않는다.**

| 오프셋 | 타입 | 내용 |
|---|---|---|
| 0 | u8 | `type` |
| 1 | u16 | `length` (payload 바이트 수) |
| 3 | ... | payload |

#### `0x01` MAP — 풀 스냅샷에만

| 타입 | 내용 |
|---|---|
| u8 | cols |
| u8 | rows |
| u8 × cols×rows | physics 값 (0=바닥 1=벽 2=수풀 3=연막), 행 우선 |

#### `0x02` TILE_CHANGES — 자기장이 타일을 부술 때

| 타입 | 내용 |
|---|---|
| u16 | count |
| (u8,u8,u8) × count | x, y, 새 physics |

#### `0x03` TILE_ALPHAS — 수풀 투명도 **(전량 교체)**

| 타입 | 내용 |
|---|---|
| u16 | count |
| (u8,u8,u8) × count | x, y, alpha |

목록에 없는 타일은 전부 불투명. **누적이 아니라 교체**라서, 플레이어가 지나간 자리의 투명 자국이 남지 않는다.

> **트래픽 실측 (BattleField 50×50)**: 맵 전체 은신타일은 172칸이지만, 레거시 근접 윈도우(21칸) 안에 들어올 수 있는 은신타일은 **최악의 경우 13칸**. 매 틱 전량 재전송해도 39B/tick = 60틱 기준 2.3KB/s로, 플레이어 8명 좌표(2.8KB/s)보다 적다. **델타 인코딩 불필요.**

#### `0x04` STORM

| 타입 | 내용 |
|---|---|
| u8 | active (0이면 이하 생략) |
| u16 × 4 | x, y, width, height |

자기장은 **벽처럼 충돌 판정되는 경계**다(서버 담당). 데미지 구역이 아니라서 플레이어가 바깥에 존재할 수 없고, 경계가 줄어들면 안쪽으로 밀린다. 또 `inset = tick × barrier_speed`로 **연속 선형 축소**라 "다음 축소" 같은 이산 이벤트가 없다 — 그래서 카운트다운 UI도 필요 없다.

#### `0x05` PLAYERS

| 타입 | 내용 |
|---|---|
| u8 | count |
| ... × count | 아래 레코드 |

**플레이어 레코드 (기본 10바이트 + 가변)**

| 타입 | 내용 |
|---|---|
| u8 | id |
| u16 | x |
| u16 | y |
| i8 | facingX (÷127) |
| i8 | facingY (÷127) |
| u8 | colorIndex |
| u8 | flags |
| u8 | effectMask |
| u8 × (effectMask 켜진 수) | 각 이펙트 잔여 비율 |
| u8 | emojiId — flags bit2(`hasEmoji`)일 때만 |

`flags`: bit0 `obscured` · bit1 `isTagger` · bit2 `hasEmoji`

`obscured`와 `TILE_ALPHAS`는 **보는 사람에 따라 달라지는 값**이라 권위 상태가 아니다. 리플레이가
기록하는 권위 프레임에서는 `obscured`가 항상 0이고 `TILE_ALPHAS`는 아예 없다. 재생할 때 시야 코어가
뷰어를 정해 다시 계산한다. 자세한 것은 `docs/REPLAY.md`를 본다.

> **"자기장 밖" 플래그는 없다.** 자기장은 서버가 충돌 판정하는 **벽**이라 바깥으로 나가는 것 자체가 불가능하다. 도달할 수 없는 상태이므로 알릴 것도 없다. 같은 이유로 엔진에는 자기장 피해 표시도, HUD에는 이탈 경고도 없다.

`effectMask`: bit0 유체화 · bit1 광란 · bit2 탈진

**이 목록에 없는 플레이어는 화면에서 제거된다.** 안 보내는 것이 곧 "안 보임"이다.

#### `0x06` REGIONS — 연막 잔여시간

| 타입 | 내용 |
|---|---|
| u8 | count |
| (u8,u8,u8) × count | 대표 타일 x, y, 잔여 비율 |

region id를 문자열로 보내는 대신 **대표 타일 좌표**로 지목한다. 엔진은 이미 그 타일이 어느 region인지 안다(플러드필 결과를 들고 있음).

#### `0x07` SELF

| 타입 | 내용 |
|---|---|
| u8 | 자기 자신 player id |

관전 모드에선 이 섹션을 보내지 않는다.

#### `0x08` — 폐기됨

일회성 연출(점멸 등)은 바이너리 섹션이 아니라 JSON 이벤트로 보낸다. 매 틱 나가는 값이 아니라서
바이너리로 아낄 것이 없고, 이벤트마다 payload 길이가 달라 모르는 이벤트를 건너뛸 수도 없었다.
점멸은 이제 `player.blinked` JSON 메시지다.

**0x08은 재사용하지 않는다.** 새 섹션은 다른 번호를 쓴다. 구버전 서버가 보낸 0x08을 신버전
클라이언트가 조용히 건너뛸 수 있어야 한다.

#### `0x09` ROSTER — 닉네임 (풀 스냅샷 / 변경 시에만)

| 타입 | 내용 |
|---|---|
| u8 | count |
| (u8, u8, bytes) × count | id, 이름 길이, UTF-8 이름 |

닉네임은 경기 중 안 바뀌므로 **매 틱 보내지 않는다.** 이것만으로 틱당 수십 바이트가 절약된다.

### 틱당 크기 추산

| 섹션 | 바이트 |
|---|---|
| 헤더 | 6 |
| PLAYERS (8명) | ~95 |
| TILE_ALPHAS (13칸) | 44 |
| STORM | 12 |
| REGIONS (4개) | 15 |
| **합계** | **~172B/tick** |

20틱/s → **3.4 KB/s**, 60틱/s → 10 KB/s. 8인 방 하나가 서버 상행 27 KB/s (20틱 기준).

## 5. 이모지

레거시(`RenderingManager.js:330-350`)와 동일한 동작: 서버가 브로드캐스트하면 해당 플레이어 머리 위에 뜨고, 약 2초간 표시되다 사라진다. 커지며 등장 → 유지 → 작아지며 퇴장하는 팝 애니메이션.

에셋은 `client/src/assets/images/01-cheer.svg` ~ `08-neutral.svg`. 프로토콜의 `emojiId`는 1~8.

| id | 파일 |
|---|---|
| 1 | 01-cheer |
| 2 | 02-wink |
| 3 | 03-content |
| 4 | 04-surprised |
| 5 | 05-flustered |
| 6 | 06-angry |
| 7 | 07-sad |
| 8 | 08-neutral |

지속시간은 서버가 굳이 관리하지 않는다. 이모지는 게임 판정에 영향이 없으니 **엔진이 자체 타이머로 뗀다** — 점멸 잔상(`BlinkFxLayer`)과 같은 취급.

## 6. 표시 옵션

플레이어 라벨은 유저 설정으로 켜고 끈다.

```ts
engine.setDisplayOptions({ showNumber: true, showNickname: false });
```

| 옵션 | 내용 |
|---|---|
| `showNumber` | 본체 안 번호 (1~8) |
| `showNickname` | 본체 위 닉네임 |

순수 로컬 설정이라 서버로 나가지 않는다. 닉네임은 ROSTER로 이미 받아둔 값을 쓴다.

## 7. 유저 설정 (설정 → 인게임)

```ts
engine.setSettings({ quality: 'low', motion: 'reduced', colorVision: 'deuteranopia' });
```

설정 스토어(`useSettingsStore`)에서 `GameCanvas`가 자동으로 밀어넣으므로, 페이지가 따로 배선할 일은 없다.
문자열→숫자 변환은 `useEngineSettings`가 경계에서 한 번만 한다.

**전부 로컬 표현 설정이다.** 서버로 나가지 않고, 서버가 보내주는 정보의 양도 바꾸지 않는다 —
안 보여야 할 플레이어는 애초에 전송되지 않으므로 클라이언트가 설정을 조작해 얻을 것이 없다.

| 설정 | 엔진에서 하는 일 |
|---|---|
| `frameRate` | Phaser `TimeStep`의 fps 상한. 런타임 변경은 내부 필드 교체 후 `sleep()`/`wake()`로 스텝 함수 재바인딩 (Phaser에 런타임 setter가 없다) |
| `resolutionScale` | 캔버스 백버퍼 = CSS 크기 × 배율, 표시 크기는 그대로. 카메라 줌에 같은 배율을 곱해 **시야각은 고정** — 해상도로 시야를 넓히는 꼼수가 생기지 않는다 |
| `motion` | `animSpeed`(장식용 진동/회전 시계 배속) + `cameraFx`(줌·흔들림·펀치 강도). `reduced`는 둘 다 0 |
| `quality` | 풀잎 개수, 연막 점 간격, 다크모드 자기장 해칭, 수풀/연막 재드로우 주기, 이펙트 링 분할 수, 점선→실선 |
| `colorVision` | 팔레트 교체 (아래) |
| `screenShake` | 광란 중 카메라 진동 on/off |
| `cameraSmoothing` | 끄면 팔로우 lerp = 1 (즉시 추적) |
| `reduceFlash` | 점멸 화면 플래시, 술래 맥동 링, 자기장 테두리 맥동을 정지 |

품질이 낮춰도 **정보는 안 지운다.** 수풀 덩어리·연막 덩어리와 잔여시간 게이지·자기장 경계·술래
링·이펙트 링은 `low`에서도 전부 남는다. 빠지는 건 같은 사실을 반복해서 말하는 장식뿐이다.

### 시계가 두 개인 이유

`motion: 'reduced'`에서 시계를 통째로 멈추면 진동은 멎지만 이모지와 점멸 잔상이 화면에 영구히
박힌다. 그래서 씬은 시계를 둘로 나눈다 — `clock`(실제 경과, 수명 판정)과 `animClock`(`animSpeed`가
곱해진 dt, sin/rot 진동). 모션을 꺼도 수명은 흐른다.

### 색각 보조

캔버스에 색행렬 필터를 씌우는 흔한 방법은 **색각이상을 시뮬레이션**하는 것이라 정작 당사자에게는
아무 정보도 주지 않는다. 그래서 여기서는 팔레트 자체를 그 유형이 구분할 수 있는 축으로 다시 고른다
(`client/src/theme/cvd.ts`). 엔진의 모든 색이 `theme/color.ts` → `game/palette.ts` 한 줄기를 지나므로
교체 지점이 하나다.

값은 Viénot–Brettel–Mollon(1999) 이색형 시뮬레이션 + CIELAB ΔE로 탐색해서 뽑았다. 플레이어 8색 중
가장 가까운 두 색의 시뮬레이션 ΔE:

| 유형 | 기존 | 교체 후 |
|---|---|---|
| 적색약 | 2.5 | 17.8 |
| 녹색약 | 3.2 | 17.1 |
| 청황색약 | 2.7 | 22.3 |

ΔE 2~3은 사실상 같은 색, 10 이상이면 "명확히 다른 색"이다. 즉 기존 파스텔 8색은 이 세 유형에게
전부 같은 색으로 보인다. 제약조건은 큰 면적(바닥·벽·수풀·연막·자기장)과 ΔE ≥ 12, 얇은 선과 ΔE ≥ 7,
정상 색각에서도 서로 ΔE ≥ 13(같은 화면을 보는 다른 사람 기준).

술래/자기장의 빨강과 유체화의 파랑은 안 건드린다 — 위험 신호의 관습이고 모양(링·깃발·사선 해칭)으로
이미 뒷받침된다. 대신 그 빨강과 충돌하는 수풀 초록·광란 주황을 Lab 색상환에서 회전시켜 떼어놓는다
(녹색약에서 수풀[1] vs 빨강[1]이 ΔE 2.1로 구분 불가였다).

HUD 명단의 색 점도 같은 팔레트를 쓴다(`hudTheme.userColors(index, mode)`) — 명단 색과 본체 색이
어긋나면 "몇 번이 누구인지"라는 그 UI의 존재 이유가 사라진다.

## 8. 정리: 엔진 공개 API

```ts
const engine = new SwitchEngine(container, { theme, mode, settings });

engine.applySnapshot(buffer);                    // 서버 바이너리 (유일한 상태 입력구)
engine.setDisplayOptions({ showNumber, showNickname });
engine.setSettings({ quality, motion, colorVision, ... });   // 유저 설정 (부분 갱신)
engine.setTheme(theme);

engine.camera.follow(id) / .free() / .setZoom(n) / .fitMap();
```

개별 setter(`player(id).setPosition(...)` 등)는 **튜토리얼과 개발 샌드박스용으로 남긴다.** 실제 게임은 `applySnapshot` 하나만 쓴다.
