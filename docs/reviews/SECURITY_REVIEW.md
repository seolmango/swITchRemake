# swITch 보안·성능 검토

검토일: 2026-08-30
검토 범위: `server-match/`, `server-game/`, `server-gateway/`, `server-supervisor/`, `shared/`, `client/src/api`, `client/src/stores`
방법: 코드 정독 + codex(gpt-5.6-sol) 교차 감사 2회. 아래 항목은 전부 코드에서 직접 확인했다.
codex가 올린 것 중 근거를 확인하지 못한 것은 "남긴 것"에 따로 적었다 - 확인하지 못한 지적을
고친 것처럼 적어 두면 다음 검토가 그 자리를 다시 안 본다.

이 문서는 **사람이 직접 읽으며 검토할 때의 안내서**다. 각 항목은 "무엇이 문제였나 → 어떻게
고쳤나 → 무엇을 보면 고쳐진 것을 확인할 수 있나" 순서다.

## 검토 순서 제안

고친 것을 되짚는 순서는 커밋 순서와 같다. `git log --oneline c425547..` 이후 한 커밋씩 본다.
커밋 메시지에 "왜 그게 문제였는지"를 적어 두었으므로, 메시지를 먼저 읽고 diff를 보는 편이 빠르다.

한 가지만 특히 봐 달라: **5번(시야 누출)과 9번(방 목록 페이징)은 게임 동작이 눈에 보이게
바뀔 수 있는 변경**이다. 나머지는 동작이 같고 안전성만 바뀐다.

## 고친 것

### 1. 인증 코드가 예측 가능했다 — `ceca532`

`Math.random()`으로 6자리 코드를 만들었다. V8의 그것은 xorshift128+라 출력 몇 개로 내부
상태를 복원할 수 있다. 공격자가 자기 주소로 코드를 몇 번 받아 시퀀스를 관측한 뒤, 피해자
주소로 재설정 코드를 발송시키고 그 값을 계산하면 메일함 없이 계정을 가져간다.

- 고침: `server-match/src/auth/verification-code.ts`가 `randomInt`로 발급한다.
- 볼 곳: 저장소에 `Math.random`이 남은 인증 경로가 없는지 — `grep -rn "Math.random" server-match/src`
  결과는 방 추첨(`quickJoin`) 하나뿐이어야 한다. 그건 보안 값이 아니다.

### 2. 틀린 코드가 소모되지 않았다 — `ceca532`

주석은 "맞든 틀리든 한 번 쓰면 사라진다"고 적혀 있었는데 `del`이 `throw` 뒤에 있어서 실패
경로에서 실행되지 않았다. 코드가 사는 5분 동안 100만 개를 전부 두드릴 수 있었다.

- 고침: `verifyVerificationCode`가 실패를 세고 5회에서 코드를 폐기한다. 성공한 코드를 지우는
  것은 뒤이은 작업(가입·탈퇴)이 끝난 뒤다 — 닉네임 중복으로 실패했다고 멀쩡한 코드를 태우면
  사용자가 메일을 다시 받아야 한다.
- 볼 곳: 가입·재설정·탈퇴 세 경로가 모두 `verifyVerificationCode` → 작업 → `discardVerificationCode`
  순서인지.

### 3. refresh 쿠키의 Secure가 꺼질 수 있었다 — `ceca532`

`secure: process.env.NODE_ENV === 'production'`인데 이 저장소에서 운영을 가르는 값은 전부
`APP_ENV`이고 `.env.example`에 `NODE_ENV`는 없다. 문서대로 배포하면 2주짜리 세션 쿠키가
평문으로 나갔다.

- 고침: `server-match/src/auth/refresh-cookie.ts` 하나로 모으고 `APP_ENV`를 본다.
- 볼 곳: 쿠키를 굽거나 지우는 모든 곳이 이 함수를 쓰는지. `grep -rn "refreshToken'" server-match/src`

### 4. X-Forwarded-For를 아무나 적을 수 있었다 — `ceca532`, `21e7456`

매칭 서버는 `trustProxy: true`였다. 즉 IP로 세는 모든 제한(로그인 시도, 인증 메일, 게스트
발급, 방 생성)이 헤더 한 줄로 무력해지고, 세션에 남는 IP 기록도 위조된다. 게이트웨이는
클라이언트가 보낸 값을 인게임 서버로 그대로 흘려보내고 있어서, 인게임 서버가 게이트웨이를
신뢰 홉으로 등록하는 순간 같은 구멍이 그쪽에도 생겼다.

- 고침: 매칭 서버는 `MATCH_TRUSTED_PROXIES`에 적힌 주소만 신뢰한다. 게이트웨이는 자기가 본
  소켓 주소를 전달 사슬 **끝에** 잇고(nginx의 `$proxy_add_x_forwarded_for`와 같다), 인게임
  서버는 사슬을 **오른쪽부터** 읽으며 신뢰 홉을 걷어낸다.
- **배포 전에 반드시**: `MATCH_TRUSTED_PROXIES`와 `GAME_TRUSTED_PROXIES`를 채운다. 비어 있으면
  모든 요청이 프록시 한 IP로 보여서 IP 기반 제한이 전역이 된다(안전한 쪽으로 실패하지만 정상
  사용자가 막힌다). 매칭 서버는 `APP_ENV=prod`에서 비어 있으면 부팅 시 경고를 남긴다.
- 볼 곳: `server-game/src/transport/ws-transport.ts`의 `resolveClientIp` 테스트 4개.

### 5. 안 보이는 사람의 좌표가 새고 있었다 — `149f4b5`

`player.blinked`는 점멸 출발 좌표를, `player.skillArea`는 스킬 원의 중심을 실어 **방 전체**로
나갔다. 스냅샷은 "안 보내는 것이 곧 안 보임"으로 만들어 두고 이 두 메시지가 그 구멍이었다.
변조 클라이언트는 시야 밖 상대가 스킬을 쓸 때마다 정확한 위치를 얻는다.

- 고침: 스냅샷과 같은 등급 판정(`snapshotAccess`)을 거친다. 관전자는 전부, 경기 중인 사람은
  시전자를 실제로 볼 때만, 세계를 안 받는 사람은 아무것도 받지 않는다. 시전자 본인은 언제나.
**소리도 같이 샜다.** `client/src/audio/matchSfx.ts:117`은 `player.blinked`마다 점멸 소리를,
120번 줄은 `player.skillArea`마다 탈진 소리를 낸다. 즉 **정직한 클라이언트조차** 안 보이는
상대가 스킬을 쓸 때마다 소리로 알려 주고 있었다. `TASKS.md`의 사운드 절이 "안 보이는 사람은
스냅샷에 없고, 없으면 소리도 없다"고 적어 둔 전제가 이 두 메시지에서만 깨져 있었다.

- **게임 동작이 바뀐다**: 예전에는 안 보이는 상대의 스킬 연출이 클라이언트에 도착은 했다(그리지만
  않았다 — 소리는 났다). 이제 도착하지 않는다. 정직한 클라이언트의 **화면**은 그대로여야 하고,
  **소리**는 달라진다. 직접 확인이 필요한 부분이 여기다: 수풀 뒤 상대가 점멸을 써도 소리가
  나지 않아야 하고, 보이는 상대의 점멸 소리는 예전과 같아야 한다.
- 볼 곳: `shared/src/visibility/core.ts`의 `sees`/`canSeePlayer`, `server-game/src/rooms/room.ts`의
  `#broadcastToViewers`.

### 6. 리플레이가 한 번도 지워지지 않았다 — `6489d46`

`control-codec.ts`의 허용 목록에 `DELETE_REPLAY`가 빠져 있었다. 소비자에는 처리기가 멀쩡히
있는데 코덱이 malformed로 잘라서 삭제 명령이 하나도 도달하지 못했다. 보관 기간이 지난 파일이
디스크에 계속 남았고 DB 행은 `deleting`에 머물렀다. 그 파일에는 경기 참가자 전원의 닉네임이
들어 있으므로 보관 정책이 문서에만 있는 상태였다.

- 볼 곳: 명령 종류를 전부 도는 테스트(`control-plane.test.ts`의 "모든 CommandType이 코덱을
  통과한다"). 명령을 새로 만들 때 이 표에 표본을 더하지 않으면 실패한다.
- **운영 확인 필요**: 이미 `deleting`으로 굳은 행과 남은 파일이 있으면 한 번은 손으로 정리해야
  한다. 코드는 다음 회차부터 정상 동작한다.

### 7. 회수되지 않던 메모리 — `e510a4c`

- 레이트 리미터: 사용자 단위 버킷을 지우는 사람이 없었다. 게스트는 접속마다 새 신원이라 지도가
  끝없이 자랐고, `releaseConnection`이 전체 키를 훑어서 지웠기 때문에 그렇게 자란 지도가 연결
  해제 비용까지 키웠다. 이제 버킷이 만료 시각을 들고 주기적으로 스스로 걷힌다.
- 좌석 표: `deleteExpired`가 있었지만 부르는 곳이 없었다. 자리를 잡고 접속하지 않으면 표가
  프로세스 수명 내내 남았다. 저장소가 스스로 치운다.
- 방 타이머: `sweep`이 이미 도는 `advance`를 위에서 한 번 더 돌고 있었다. 100ms마다 모든 방이
  두 번 전이했다.

### 8. 제재가 진행 중인 방에 반영되지 않았다 — `ac7e667`

`KICK_USER`는 인게임 서버에 처음부터 구현돼 있었는데 보내는 사람이 매칭 서버에 없었다. 제재는
세션 행만 지우고, 이미 발급된 access token은 만료까지 살아 있으며 인게임 서버는 계정 상태를
모른다. 밴당한 사람이 그 경기가 끝날 때까지 그대로 놀았다.

- 고침: `RoomsService.evictActor`를 제재(WARN 제외)와 계정 탈퇴에서 커밋 뒤에 부른다.
- 볼 곳: 트랜잭션 **밖**에서 부르는 이유(다른 프로세스로 나가는 왕복이라서)와, 실패해도 제재가
  유효한 이유.

### 9. 방 목록이 매번 전체를 읽었다 — `51f1ae6`

대기 중인 방을 전부 읽어 요약한 다음 20개로 잘랐다. 방이 500개면 목록 한 번에 Redis 왕복
1000번이고, 그건 사람이 가장 자주 누르는 화면이다.

- **동작이 미세하게 바뀐다**: `total`이 정렬 집합의 크기라, 방금 죽은 서버의 방이 잠깐 섞여
  실제 표시 수보다 클 수 있다(최대 heartbeat TTL 6초). 페이지에 20개 미만이 보일 수 있다.

### 10. 게이트웨이 — `21e7456`

- 경로 접두사 검사를 `%2e%2e`로 우회할 수 있었다. `new URL()`이 정규화하므로
  `/replays/%2e%2e/internal`이 백엔드에서 `/internal`이 됐다. 지금은 인게임 서버가 그 두 접두사
  외에 아무것도 서빙하지 않아 실제 피해가 없었지만, 내부용 엔드포인트가 하나라도 생기면 열린다.
- 브라우저의 refresh 쿠키와 access 토큰이 맵 번들·리플레이 요청과 WS 업그레이드에 실려 인게임
  서버로 갔다. 설계상 인게임 서버는 계정을 모르고 접근 통제는 전적으로 좌석 티켓이 한다.
- `requestTimeout = 0`은 공개 프록시에서 느린 본문 하나가 연결을 무기한 잡는다.

### 11. 표 검증의 상수 시간 응답이 실제로는 동작하지 않았다 — `e510a4c`

지연이 작업 **앞**에 있어서 총 시간이 "고정 지연 + 작업 시간"이었다. 남은 시간을 작업 뒤에
채운다. 대신 작업 전에 한 번 양보해서, 이미 닫힌 소켓을 위해 자리를 잡는 일은 그대로 막는다.

### 12. 인증 경로가 매번 세션 테이블 전체를 UPDATE했다 — `8cc1020`

`purgeExpiredEncryptedIps`는 조건에 사용자 구분이 없어 세션 테이블 전체를 훑는다. 그런데
로그인, 토큰 회전, 세션 목록 조회가 매번 이걸 불렀다. 게다가 그 테이블은 **지우는 사람이 없어서**
계속 커지기만 했다 - 세션 삭제는 밴과 탈퇴 경로에만 있었고, refresh는 회전할 때마다 새 행을
만든다(활성 사용자 한 명이 하루 100행쯤).

- 고침: 정리는 이미 도는 타이머만 부른다. 보관 회차에 끝난 세션 삭제를 추가했다(`SESSION_RETENTION_DAYS`, 기본 30일).
- 볼 곳: 살아 있는 세션이 지워지지 않는지 — 조건이 "끝났고(폐기 또는 만료), 그러고도 보관 기간이 지났다"이다.

### 13. 제재 취소가 사용자 행을 잠그지 않았다 — `8cc1020`

`apply()`는 사용자 행을 `for('update')`로 잠그는데 `revoke()`는 제재 행만 잠갔다. 새 BAN 적용과
옛 BAN 취소가 겹치면 취소 쪽의 "다른 활성 BAN이 있나" 조회가 아직 커밋되지 않은 새 BAN을 못 보고
계정을 ACTIVE로 되돌린다. 1분 뒤 조정 루프가 고치지만 그 사이에는 밴당한 사람이 로그인한다.

- 볼 곳: 두 함수의 잠금 **순서**가 같은지. 순서가 어긋나면 이번에는 교착이 생긴다.

### 14. GAME_RESTRICT 제재가 아무 일도 하지 않았다 — `5bccb0d`

enum과 관리자 DTO에만 있었고 읽는 곳이 없었다. 운영자는 밴보다 가벼운 처분을 걸었다고 믿고
대상은 그대로 놀았다. 방으로 들어오는 길이 전부 `requireActor`를 지나므로 판정을 거기 넣었다.

- **동작이 늘어난다**: 경기 제한 계정은 방 생성·참가·빠른 참가·코드 참가·재접속이 모두 403이다.
  화면은 `rooms.errors.gameRestricted` 문구를 보여 준다.
- 볼 곳: 제한이 **로그인은 막지 않는지**. 막으면 밴과 구분이 사라진다.

## 확인했지만 문제가 없던 것

읽고 넘어간 것도 적어 둔다 — 다음 검토가 같은 곳을 다시 파지 않도록.

- SQL 인젝션: drizzle 파라미터 바인딩이 일관되고, 관리자 화면의 원시 SQL도 전부 바인딩이다.
- 방 비밀번호: `timingSafeEqual`로 비교한다.
- 리플레이 표: 1회용·60초·저장소 키 일치까지 확인하고, 파일 키는 정규식으로 경로 조작을 막는다.
- 클라이언트 XSS 표면: `dangerouslySetInnerHTML`·`innerHTML`·`eval`이 하나도 없다.
- 토큰 보관: access는 메모리, refresh는 httpOnly+signed+sameSite=strict 쿠키.
- 입력 패킷: 6바이트에 좌표·속도를 실을 자리가 없고 스킬 판정은 전부 서버다.
- 결과 스트림: 참가자가 배정 명단의 부분집합인지 검증한다.
- `.env` 계열은 전부 gitignore되어 커밋 이력에 없다.
- 한 사람 한 방 표(`userActiveRoom`)의 30초 TTL은 인게임 서버 heartbeat가 갱신한다.

## 고치지 않고 남긴 것

### 등록부(registry) 발행 증폭 — 측정 먼저

방 하나에 사람이 들락거릴 때마다 **전체 방과 전체 좌석**을 순차 `await`로 다시 쓴다. 100방
8명이면 발행 한 번에 좌석 동기화만 왕복 1600번이고, 그게 60Hz 게임 루프와 같은 이벤트 루프에서
돈다. `GAME_MAX_ROOMS=100`은 측정값이 아니라 보수적인 출발점이므로, 실제 상한은 여기가 정할
가능성이 크다.

고치지 않은 이유: 좌석 표 갱신 주기를 늦추면 Redis가 키를 잃었을 때의 복구가 같이 늦어진다.
그 균형은 부하를 재고 정해야 하는 값이지 짐작으로 바꿀 값이 아니다. **부하 테스트에서 가장 먼저
볼 지표는 heartbeat 주기의 `loopLagMs`다.**

### 관전자의 전지적 시야

탈락자는 맵 전체를 본다. 부계정으로 들어와 일부러 빠지면 합법적인 고스팅 통로가 된다. 이건
설계 선택이라 코드로 정할 문제가 아니다 — 감수한다면 그대로 두고, 아니면 관전 시야를 좁히는
규칙이 필요하다.

### 로그아웃이 서버에 닿지 못해도 조용히 성공한다

`client/src/api/http.ts`의 `logoutAndCreateGuest`는 네트워크 실패를 삼키고 이 탭만 게스트로
바꾼다. 주석대로 "이 탭에서 계정이 되살아나지 않게" 하려는 의도는 맞지만, 서버 세션과 refresh
쿠키는 그대로라 다른 탭에서 계정이 살아 있다. 사용자에게 알리려면 화면 쪽 처리가 필요해서
이번 회차에서는 건드리지 않았다. [codex 지적, 코드로 확인함]

### 확인하지 못한 codex 지적

근거까지 따라가지 못한 것들이다. 다음 회차에서 먼저 볼 목록으로 남긴다.

- `reports.service.ts` — 이미 `ACTIONED`인 사건에 제재를 다시 걸 수 있다(중복 클릭·재시도)
- `user.service.ts` — 비밀번호 변경과 타 세션 폐기가 한 트랜잭션이 아니다
- `registry.ts` — 인계 시 active-room 표를 CAS 없이 덮어쓴다(주석은 의도된 선택이라고 설명하지만,
  인계 도중 사용자가 다른 방으로 옮긴 경우는 그 설명이 안 덮는다)
- `result-outbox.ts` — 큐 flush가 `shift()` 기반이라 대량 복구 시 O(n²)
- `sanction.service.ts` — 매분 조정 루프가 사용자별 트랜잭션을 직렬 실행한다

### JSON 프레임을 레이트 리밋 전에 파싱한다

`ws-transport`가 `parseClientMessage`를 먼저 부르고 그 뒤에 한도를 본다. 순서를 뒤집는 것이
교과서적이지만, 프레임이 2KB로 묶여 있어 파싱 비용이 무의미하고, 뒤집으면 한도 초과 응답이
`requestId`를 잃어 클라이언트가 어느 요청이 막혔는지 모르게 된다. 지금은 그대로 둔다.
